# Package contract

contractVersion: 1.4.0

A **package** is the unit Phi distributes: one skill, wrapper, MCP connector, or
plugin, with a manifest, an exact file list, and a version. This contract defines
the manifest fields every package shares, the file list, the archive, the registry
index, and the installer. Type-specific rules live in the type's own contract (for
plugins, [plugin contract](plugin.md)); wrapper and connector packages are defined
by later contracts and are rejected by v1 installers. See
[content distribution design](../design/phi-content-distribution-design.md) §5–§6.

## 1. `phi-package.yaml` (shared fields)

| Field           | Required | Rule                                                                                                                           |
| --------------- | -------- | ------------------------------------------------------------------------------------------------------------------------------ |
| `schemaVersion` | yes      | `1`                                                                                                                            |
| `id`            | yes      | `^[a-z][a-z0-9-]{1,63}$`; unique per `type` within a registry                                                                  |
| `type`          | yes      | `skill`, `plugin`, `wrapper` (1.1.0, [wrapper contract](wrapper.md) § 3), or `mcp` (1.1.0, [connector contract](connector.md)) |
| `version`       | yes      | semantic version `MAJOR.MINOR.PATCH` (optional `-prerelease`)                                                                  |
| `title`         | yes      | 1–80 characters                                                                                                                |
| `summary`       | yes      | 1–300 characters                                                                                                               |
| `minAppVersion` | no       | semantic version; an app older than this shows the package but refuses to install it                                           |
| `requires`      | no       | `{ coreTools: [<tool name>…] }`: engine tools the package relies on (for example `skill_run`); a missing one refuses install   |
| `dependsOn`     | no       | `[{ id, type, version }]`: other packages, `version` a semver range (`^1.2.0`, `>=1.0.0 <2`); installed first if missing       |
| `files`         | no       | `files.json`; when present the file list (§ 2) is authoritative                                                                |

Type-specific fields follow:

- **`type: skill`** — the package root **is** the skill directory: `SKILL.md` and the
  skill's own files next to `phi-package.yaml`. `id` equals the skill's `name`. The
  skill must validate as a standalone skill (skill contract).
- **`type: plugin`** — plugin contract § 2 (`toolPrefix`, `components`,
  `environments`).
- **`type: wrapper`** (1.1.0) — files keep their wrapper-tree paths; installed into the
  shared wrapper tree (wrapper contract § 3–4).
- **`type: mcp`** (1.1.0) — the `connector` block (connector contract § 2).

Unknown top-level keys are errors.

## 2. `files.json`

Generated by the package builder, never written by hand:

```json
{ "version": 1, "files": [{ "path": "SKILL.md", "sha256": "<64 hex>", "size": 1234 }] }
```

- `path` is relative, `/`-separated, without `.` or `..` segments, and unique; the
  list is sorted by `path` and excludes `files.json` itself.
- The builder takes **git-tracked files only** and rejects run leftovers
  (`.nextflow/`, `.nextflow.log*`, `work/`, `results/`, `.DS_Store`, `__pycache__`,
  and anything `scripts/check-resources.mjs` rejects).
- Symlinks, device files, and empty directories are not packaged.

## 3. Archive

One `<type>-<id>-<version>.tar.gz` per package: the package root's files at the
archive root (no leading directory), regular files only, including
`phi-package.yaml` and `files.json`.

## 4. Registry index

`index.json` at the registry root:

```json
{
  "schemaVersion": 1,
  "generatedAt": "<ISO 8601>",
  "packages": [
    {
      "id": "scanpy",
      "type": "skill",
      "version": "1.0.0",
      "title": "…",
      "summary": "…",
      "archive": "skill-scanpy-1.0.0.tar.gz",
      "sha256": "<64 hex>",
      "size": 12345,
      "minAppVersion": "0.9.0",
      "dependsOn": [],
      "requires": { "coreTools": ["skill_run"] },
      "category": "single-cell"
    }
  ]
}
```

`archive` is a path relative to the index (a local directory registry) or an
`https://` URL. `category` and `preview` are optional catalog metadata. A registry may
list several versions of one package.

### 4.1 Signature (1.2.0)

A registry may carry `index.sig.json` next to `index.json`:

```json
{ "version": 1, "keyId": "<16 hex>", "signature": "<base64>" }
```

`signature` is an ed25519 signature of the exact bytes of `index.json`; `keyId` is the
first 16 hex characters of the SHA-256 of the raw 32-byte public key. The app embeds
the trusted first-party public keys. Reading a registry gives it a **trust tier**:

| Registry                                                                    | Tier         |
| --------------------------------------------------------------------------- | ------------ |
| explicitly engine-owned legacy migration registry                           | `builtin`    |
| valid signature by an embedded key                                          | `official`   |
| no `index.sig.json`, or signed by a key Phi does not know                   | `imported`   |
| `index.sig.json` unreadable, or an embedded key's signature does not verify | **rejected** |

Archives are covered by the signature through their `sha256` in the index. A remote
(`https://`) package registry must be `official`; the signed Phi Packages release
implements this requirement. Local directory registries and locally materialized
repository snapshots retain `imported` trust and require an explicit installation
choice. Website discovery metadata does not grant signature trust.

Current builds ship no bundled domain-content registry. `builtin` remains for
legacy installations and explicit engine-owned migrations. A raw connector source
directory receives imported trust; its name or location cannot grant builtin trust.

### 4.2 Content icons (1.3.0)

An entry may include `iconAsset: { "path": "icons/skill-scanpy-1.0.0.svg", "sha256":
"<64 lowercase hex>", "size": 1234 }`. `path` is a safe, `/`-separated relative
path with no empty, `.` or `..` segments, backslashes, drive prefixes, URL syntax,
encoded path segments, or control characters. Only `.svg`, `.png`, `.webp`, `.jpg`,
and `.jpeg` are supported. `size` is an integer from 1 through 262144 bytes.

The optional source icon uses the corresponding default `icon.<extension>` filename
at the package root, beside its manifest or `SKILL.md`. Lookup prefers SVG, PNG,
WebP, JPG, then JPEG. Generated wrapper packages check their family root, then their
root `wrapper/` adapter directory; arbitrary nested images are not catalog icons.
The builder includes the icon in the package's `files.json` and archive and publishes
an exact sidecar copy at `icons/<type>-<id>-<version>.<extension>`. Sidecar size and
SHA-256 must match before display; a signed index covers this descriptor like archive
metadata. Installed icons remain verified package files. Absence of `iconAsset`
keeps older registry entries valid and uses the type fallback. See
[content icon convention and attribution](../content-icons.md).

### 4.3 Official catalog sources (1.4.0)

HTTP connectors use `https://phi.omicsagent.cn/api/mcp` and the fixed per-ID detail
API directly. Validated complete HTTP manifests and same-origin icons become local
installable packages in `~/.phi/cache/registries/phi-connectors-api/`; the normal
connector path does not fetch a GitHub snapshot. These API packages retain
`imported` trust and are shown as `Phi 官网`. Authorization-blocked entries remain
visible with their restriction. API failure uses a validated connector cache,
then the original signed release source with an explicit fallback notice. User
GitHub imports retain their own provenance and remain available.

Phi first reads `https://phi.omicsagent.cn/api/catalog`. Its commit identifies a
fixed snapshot of `dxsbiocc/phi-packages`. Phi validates and materializes the complete
skills, connectors, plugins, and wrappers into its local package format without
executing repository code. Short skill metadata versions such as `1.3` become
`1.3.0`. This source retains `imported` trust because it has no release signature.
Skills may be flat or nested under group directories. Each `SKILL.md` directory
becomes its own package, with `metadata.category` or its parent group path retained
as catalog metadata; grouped API identifiers resolve to that leaf package ID.
When `/api/catalog` declares `skillGroups`, Phi reads the complete paginated
`/api/skills` list and preserves `group`, `groupLabel`, declared group order and
empty groups. These official fields override source categories. Classification
changes publish a new immutable index generation even when the repository commit
is unchanged, reusing verified archive bytes without reinstalling the packages.

Website generations live under
`~/.phi/cache/registries/phi-packages-website/generations/<commit>-<index-sha256>/`.
The index and every prepared archive, manifest, and icon are checked against their
recorded sizes and hashes before use; `current.json` selects a complete generation
atomically. Opening a catalog explicitly refreshes website metadata. Successful
agent installations notify open resource views to reread their installed state.
The index and cache metadata also record `materializerRevision`. A newer content
builder rebuilds older generations from the pinned snapshot even when the commit
is unchanged, so recomputed diagnostics replace stale notices atomically.
Nextflow `plugin/<id>` imports are runtime plugin dependencies; their declarations
remain in the packaged configuration and are not missing local wrapper files.

If the website is unavailable, Phi uses a valid website cache, then falls back to
`https://github.com/dxsbiocc/phi-packages/releases/download/catalog-v1/` with visible
source feedback. Signed release generations remain under
`~/.phi/cache/registries/phi-packages/generations/<index-sha256>/`; their archives
are fetched only for the selected dependency plan. Both sources use the stable
identity `phi-packages`; managed generation paths are not user-added directories.

## 5. Install

1. **Plan** — resolve `dependsOn` against installed packages and the registry; refuse
   on a missing dependency, a version conflict, `minAppVersion`, or a missing core
   tool; show the plan (packages, archive sizes, environments the packages declare).
2. **Fetch and verify** — read or download each archive; its SHA-256 and size equal
   the index entry.
3. **Stage** — extract into `~/.phi/.staging/<random>/`, rejecting absolute paths,
   `..` segments, links, and any entry type other than a regular file or directory.
4. **Check** — every staged file is listed in `files.json` with the same size and
   SHA-256, every listed file exists, and the manifest equals the index entry's `id`,
   `type`, and `version`. Then the type's own validator runs (skill contract; plugin
   contract via the plugin loader).
5. **Commit** — skill, plugin and MCP packages atomically rename into
   `~/.phi/packages/<type>/<id>/<version>/` and write `.source.json` there:
   `{ "registry": "<registry id or path>", "id", "type", "version", "sha256", "installedAt", "installedBy": "user" | "dependency", "trust": "builtin" | "official" | "imported" }`
   (`trust` added in 1.2.0; a missing `trust` reads as `builtin` for the bundled
   registry and `imported` otherwise).
   Plugins then go through the plugin loader's install or upgrade (plugin contract
   § 4). Wrapper files merge into `~/.phi/wrappers/tree/`;
   `~/.phi/wrappers/tree.json` records exact per-package ownership and provenance.
   One active version per `type`/`id`.
6. **Environments** are not built at install (built on first use, or from the
   environment panel), except as the plugin contract's upgrade rule requires.

The main agent can discover additional capabilities with `capability_search` and
request their installation with `capability_install`. Discovery queries the
[official catalog API](https://phi.omicsagent.cn/api/catalog) first, then resolves
the results against the application's prepared registries. Website `packageUrl`
fields describe individual content files; complete resources come from the fixed
official repository commit. Package archives and dependencies are validated through
the existing installer, and signed release trust is never fabricated for a snapshot.

Agent-initiated installation and enablement always require the user's explicit
approval, including in automatic permission mode. The approval identifies the
source, exact versions, dependencies, download size, and task-specific reason.
Candidates belong to their originating session, and the installer rechecks the plan
after approval and queueing. Rejection, cancellation, or a retired run cannot start
an installation. Plan mode permits discovery but blocks installation.

`find_skills` checks the application catalog before searching external skills.
External installation requires a separate approval naming the repository, skill,
and fixed Git commit, and imports the skill through the same package validator and
installer with `imported` trust. Live in-process sessions refresh skills, specialist
tools, and connectors after installation without restarting their current task.
The experimental RPC route returns `requiresSessionRefresh` instead and tells the
user to reopen the conversation before using newly installed resources.
Connector installation does not supply credentials or complete authentication.

**Upgrade** installs the new version beside the old and switches atomically; the
old version is removed after the switch. **Uninstall** refuses while another
installed package depends on it; it removes the package, drops its environment
references, and removes packages that were installed only as its dependencies and
are no longer needed. A staging directory older than one day is removed on start.
Cleanup and extraction reject symbolic links at the agent and staging roots before
reading, writing, or removing staged content.

## 6. Registries, updates, and offline import (1.2.0)

- **Known registries** are the fixed official Phi Packages source first, followed by
  the local directory sources the user added. Only those user sources are kept in
  `~/.phi/state/registries.json`:
  `{ "version": 1, "registries": [{ "id": "<16 hex of sha256(path)>", "kind": "directory", "path": "<absolute>", "addedAt": "<ISO 8601>" }] }`.
  They survive restarts; removing one never uninstalls what was installed from it.
- **Updates are prompted, never silent.** An installed package has an update when a
  known registry whose tier is not lower than the package's recorded `trust`
  (`builtin` = `official` > `imported`) lists a higher version of the same `type`/`id`
  that this app may install (`minAppVersion`, core tools). The registry recorded in
  `.source.json` is preferred when several offer one. Packages the app keeps up to date
  itself are not listed. Previously bundled domain plugins and wrappers may receive
  signed official updates. Updating is the § 5 upgrade.
- **Offline import** installs a single package archive (§ 3) chosen by the user: the
  archive's `phi-package.yaml` and `files.json` stand in for the index entry (its
  SHA-256 and size are those of the file), the install runs § 5 with tier `imported`,
  and `dependsOn` must be satisfied by installed packages or known registries.
  Importing a whole registry is adding a directory registry.

## 7. Versioning

`contractVersion` follows the content distribution design §4.4: minor versions are
additive only (a new package `type`, new optional fields); anything else needs a
decision record and a deprecation window.
