# 能力自主扩展与安全管控设计

日期：2026-10-17
更新：2026-10-18（评审修订：审查与签名分离、执行经纪人、构建期管控、草稿血缘、项目版本固定、授权对象、审计威胁模型）
状态：设计稿，**不进入内部测试版范围**。内部测试版继续遵循现有的 [`capability_search` / `capability_install` / `find_skills` 和 package 合约](../contracts/package.md)。本文描述后续产品行为；其中“已审查官方能力按需自动安装”需要在上线前修订合约并实现，不能解释为当前已有行为。
决定记录：[能力自主扩展与安全管控](../decisions/capability-autonomy-safety.md)。

## 1. 目标与用户流程

当任务缺少能力时，Phi 先用已有能力，再搜索合适的能力，补齐后继续原任务。用户只需理解能力的用途、来源、数据去向和影响；skill、wrapper、connector、plugin 等实现类型放在详情中。成功标准是任务完成及结果可追溯，而非安装或创建数量。

| 来源                         | 发现与加入                                                                                                       | 默认作用范围       |
| ---------------------------- | ---------------------------------------------------------------------------------------------------------------- | ------------------ |
| Phi 已审查并可验证的官方能力 | 可搜索；需要时由宿主校验来源、内容、审查记录和运行条件后自动安装、启用，告知用户结果                             | 普通会话和项目会话 |
| 第三方能力                   | 项目会话可以检索元数据，不因检索运行代码；用户查看来源、用途、权限和安装计划后一次确认，再安装、受限试运行、启用 | 当前项目           |
| 从已完成任务学习的能力       | Phi 在项目内发现重复流程，生成不可自行执行的草稿；用户查看步骤、适用范围和权限后，一次批准受限试运行及通过后加入 | 当前项目           |

这里的“官方”限于 Phi 内置或由 Phi 信任的密钥验证签名的发布内容，不由网站名称决定。当前官网目录中的未签名内容在 [package 合约](../contracts/package.md)中仍是 `imported` 信任等级；签名发布链路建立前，这些内容继续走需确认的路径。已安装能力仍须符合当前项目的数据策略；来源可信不等于适合该任务或保证结果正确。

免安装审批的自动安装进一步限于同时满足以下条件的 **reviewed 官方集合**：发布签名有效、经过人工审查、可由锁定依赖与可复现构建得到、并在目录中固定内容 hash。签名只证明发布者与内容完整性，不证明代码已被审查或适合当前任务；只有签名而未审查的官方内容仍须一次确认。免审批路径意味着用户不会看到内容，因此审查记录必须独立于签名存在。

第三方能力的安装文件可由 Phi 集中管理，但**启用范围限于批准它的项目**。另一项目要使用同一已安装版本，仍须查看权限并批准启用；不重复下载并不等于跨项目自动授权。能力包升级按 §6 单独处理，并受项目固定版本约束。

reviewed 官方集合的**首次按需安装**可以免安装审批；已有能力的**版本升级**仍须用户确认，因为全局活动版本会变化，且项目可能固定在旧版本。安装或启用不能预先授权数据外发、删除、付费提交或新增凭据用途；这些操作按 §4 单独确认。计划模式只允许搜索，不执行安装。

## 2. 发现、学习与工具设计

保持按动作划分的工具：现有 `capability_search`、`capability_install`、`find_skills`，以及后续新增的 `capability_create`。工具用 `type` 区分能力类型，不新增按类型拆分的一组同义工具。签名校验、来源分级、可用范围和候选排序由宿主决定，智能体只在返回的候选里说明适用理由。

候选先检查输入格式、物种、数据规模、环境和数据限制，再按已安装、已审查官方、第三方排序；适用性不明时显示“待核实”，不自动选用。质量或调用次数只影响合格候选的排序，不改变信任等级。没有合格候选时，Phi 可以解释第三方方案或把已成功执行的流程整理为项目草稿。

学习由**已完成的项目任务**触发，不持续运行监控智能体，也不定时扫描完整日志。审计日志只记录脱敏元数据，不足以重建可靠流程；识别重复步骤和生成草稿应使用项目内仍获准保留的会话执行记录。已删除的会话不参与学习。敏感数据需要发送给模型服务时遵守项目数据策略；没有相应授权时只能作本地可行的检测或保留建议，不能悄悄上传记录。

草稿本身不运行，也不自动发布、提升为全局能力。草稿由已完成任务的执行记录**确定性生成**：以真实执行的命令、参数、输入输出和产物为主体，模型只负责命名、归类、描述和适用条件，不采用在线智能体自由撰写整段能力代码的方式。草稿可先保存为“未验证”，但不进入自动执行候选。用户批准时看到具体内容、来源任务、所需权限、非敏感验证样例、适用范围和已知限制；批准覆盖限定的试运行及“通过后在本项目启用”。试运行失败则保留草稿并说明原因；内容或权限变化后重新批准。没有可核对的预期结果时仍可保存草稿或进行经授权的一次性试用，但不能标为已验证；“已验证”要求把期望结果固化为可重复的验证样例，环境、依赖或权限变化后自动退回“未验证”。草稿记录其引用的会话、项目和执行记录；来源会话或项目被删除、项目策略收紧时，相关草稿退回“未验证”并退出自动执行候选，不能只停止未来学习而保留已经生成的草稿。首批优先处理已验证脚本和流程封装；connector 与 plugin 的自动创建在执行保障成熟后再评估。

## 3. 一次确认的范围与任务续接

第三方能力先获取并暂存用于静态检查的内容，期间不执行包代码。安装卡片由宿主给出确切来源、版本、内容 hash、依赖、下载量、文件和网络权限、试运行范围，以及它为何有助于当前任务。用户一次确认**当前安装计划、受限试运行和通过后启用**；实际内容、计划或权限改变则原确认失效。拒绝后 Phi 可以寻找影响实质不同的方案，不得换用 bash 等工具完成被拒绝的同一安装或操作，也不反复索要同一权限。

学习草稿的确认卡片以同样方式展示草稿及验证条件。官方能力自动安装也显示来源、版本和安装结果，但不弹出安装审批。需要认证时由用户输入凭据；安装、认证或试运行完成后返回原任务，不要求用户重述需求。切换会话保留待处理状态；应用重启后先核对已提交任务的状态，再决定是否继续，不能盲目重复上传或计费。

宿主内部把“安装”与“授权”记录为两个对象：`install` 表示内容已校验、可逆、低风险；`grant` 表示项目级、持久、可撤销、可过期的启用与操作范围。一次确认可以同时创建两者，但撤销、过期、重新确认和审计都作用于 `grant`。卸载或停用能力不等同于撤回已经发生的数据外发、费用或不可逆删除。这样“卸载即撤销”不会成为含义模糊的承诺。

## 4. 具体操作的授权

能力的安装或加入，与使用它处理数据是两项决定。对数据外发、删除、凭据用途变化、不可控费用等操作，以**边界明确的业务操作**请求授权，而不是对每次底层工具调用重复弹窗。

授权卡片展示具体数据或字段、目标服务、操作、可能产生的远端任务、费用上限、有效期限和可撤销范围，并标明替代路径。同一批任务的分页、状态轮询可以包含在授权内；自动重试还须有次数上限及幂等性或执行状态证据。新增文件、扩大数据范围、更换服务、提高费用、版本或权限变化、授权过期或项目策略收紧时重新确认。不提供跨任务的高风险“始终允许”。无法约束费用上限的付费操作不自动执行。

项目是数据策略的基础范围，单个文件可以更严格。无法判定是否敏感的内容先暂停外发，请用户确认。模型服务也是外部目的地：主模型、审查模型、子智能体和由会话记录生成的摘要都不得扩大已批准的数据与服务范围。只读工具也不能因“只读”就豁免外发规则。

## 5. 宿主强制的安全底线

这些控制对官方、第三方和学习能力都适用；需要执行第三方或学习所得代码时，缺少相应保障就不开放该路径。

- **来源与内容**：对非内置官方包校验发布签名，并检查包文件 hash、依赖和精确版本。`imported` 内容即使来自官网目录，也不能作为已签名官方包自动安装。内容、工具描述或权限变化须重新判定信任与授权。自动安装只适用于 reviewed 官方集合；宿主在启动和安装时检查吊销清单，签名密钥被吊销或目录撤回版本时停用相关能力并告知用户。目录不得以低于已安装版本的“新包”触发降级；密钥轮换通过应用更新分发新的受信公钥，旧包在过渡期内用新旧密钥重新校验。
- **权限与执行**：能力声明文件、进程、网络、凭据与远程访问范围；宿主在运行时强制执行，超出即拒绝。第三方与新建代码的试运行和正式运行都要隔离文件、进程、凭据、网络出口、时间、内存及付费预算。限制须覆盖 OMP 工具、子智能体、MCP stdio 和其子进程，不能靠提示词或审批卡代替。这些限制由**单一执行经纪人**统一落实：能力声明编译为文件、网络出口、凭据、进程与资源预算，skill、脚本工具、wrapper、MCP stdio、OMP 扩展和子智能体都必须经该路径；没有经纪人时不开放新的免审批执行路径。
- **构建期**：环境构建、依赖解析和 MCP 运行时下载同样属于代码执行与网络访问。环境只从批准的索引或镜像安装锁定版本的依赖并校验 hash；构建脚本和安装钩子按运行期同等隔离与审计。只管控运行期会让供应链从构建期绕过权限声明。
- **OMP 扩展**：受控任务不加载未经验证的 OMP 扩展。允许记录绑定精确内容与版本；发生变化重新检查。远程或 HPC 的约束必须在执行端落实，审批结果回传桌面端；没有同等保障时该执行路径保持关闭。
- **凭据**：继续使用可用的系统加密存储，按 connector 和用途隔离；智能体不能取得明文，用户负责输入。现有 `mcp-credentials.json` 已存放加密值，是否迁入独立钥匙串项需单独评估，不能把文件名当作明文存储的证据。
- **审查模型**：独立于执行智能体调用，不携带其会话上下文，也不调用工具；可以提示可疑代码、指令注入或重复能力。结论只能加严，不能跳过宿主检查。它不是每次安装的必经关卡；不可用时不显示“已通过语义审查”，确定性检查和相应用户确认仍必须完成。任何无法完成的强制安全检查都不能被人工确认替代。
- **不可改写的规则**：能力不能修改审批策略、系统提示词、hooks、来源配置或凭据存储，也不能自行授权。外部内容不能覆盖用户拒绝记录。每次会话的安装、创建和资源消耗受上限约束。

## 6. 版本、回滚和结果记录

每个 `type` / `id` 只有一个全局活动版本。能力包升级需审批，卡片列出受影响项目及版本变化；运行中的任务先按启动时版本完成，再切换活动版本。新任务使用新版。用户重新运行旧分析时，Phi 显示原结果使用版本与当前版本的差异；结果变化本身不视为升级失败。

评审修订：项目默认**固定在批准 `grant` 时记录的能力版本**，全局活动版本只作为新项目和新任务的默认值。升级是项目内的显式动作，或在下一个任务开始前要求确认。这要求能力包层保留旧版本，或能按来源与内容 hash 重新取回并校验；在此之前至少显示版本变化提示，不得静默替换。运行中的任务仍按启动时版本完成。

回滚只针对能力包：旧版及其依赖可取得、校验通过且可恢复运行条件时切回；不可取得时说明原因。回滚能力版本不能撤回已经发送的数据、产生的费用或不可逆删除。Phi 软件和 OMP 运行时的升级遵循各自的发布与验证流程，不使用能力包回滚入口。

结果旁保留实际使用的能力版本、来源和内容 hash、模型版本、运行环境、关键参数、输入标识、输出位置、验证结果及必要的人工调整；敏感参数脱敏，缺失信息显式标出。这是**历史执行记录**，不锁住项目后续运行的能力版本，也不承诺新版本得到完全相同的科学结果。Methods 草稿只引用已有记录，未记录的实验条件和引用留待用户补充。

## 7. 审计与自动学习材料

单独长期记录实际安装和升级、批准与拒绝、能力启用、越权拦截及必要的内容变化证据；写入前脱敏，只在本地保存，不自动上传。项目关联记录随项目保留，用户删除项目时可以清除；全局能力包的安装与升级记录保留到用户明确清理。达到容量上限前提示处理；不能静默丢弃新的审批证据，也不能在记录无法写入时继续新的受控安装。实现可采用分段、只追加记录，清理规则与防篡改手段另行确定。

审计写入必须发生在智能体无法改写的位置：由宿主进程持有写句柄，使用只追加分段和哈希链，并在启动时校验连续性。若审计文件位于智能体可写的宿主路径，它只能被视为运维证据，不能作为对抗性证据；这一点必须写进威胁模型，不能用“不可改写规则”代替实现。

普通内部运行日志中的搜索与工具调用元数据遵循 14 天默认保留期；会话时间线按会话自身的保留规则保存。审计日志不保存对话正文或完整工具输出。自动学习使用获准保留的项目会话执行记录，而非把审计日志当作训练材料。用户删除会话或项目后，对应内容不再用于后续学习。

## 8. 失败与恢复

安装或试运行失败时，保持原任务和输入，说明失败步骤，清理未启用内容；未通过检查的能力不能变成可用能力。认证中断时保留返回入口，恢复后重新检查策略与授权。用户拒绝后不能绕道执行同一操作。用户停止或应用重启时，使未执行的批准失效；已提交的远端作业先查状态，避免重复提交。

停用能力、能力包版本回滚、本地文件恢复和取消远端作业分别报告结果。无法恢复的影响明确展示；普通停止或版本回滚不得被描述成撤回外部影响。敏感项目的策略收紧会使不再符合策略的授权失效，并阻止后续调用。

## 9. 实施顺序与验收

各阶段均在内部 beta 之后。当前 `capability_install` 对智能体发起的安装一律要求审批；在推出官方可信能力自动安装前，须更新 package 合约、发布链路和相关测试。本设计不改变当前产品或已安装包。

评审修订后的顺序是：执行经纪人先于官方自动安装，构建期与运行期同时落地，学习路径最后。理由是一次性风险可以先收窄，而学习草稿的风险是持久化的——一次错误批准会长期留在项目里。

1. **执行前提**：确定权限 manifest 与宿主强制点，落地单一执行经纪人（文件、网络出口、凭据、资源与费用预算）、构建期管控、`install` / `grant` 对象、基本审计、停用与吊销机制。未验证的执行路径保持关闭；没有经纪人不得新增免审批路径。
2. **官方路径**：以 reviewed 白名单（签名 + 人工审查 + 可复现构建 + 固定 hash）验证“发现 → 自动安装 → 继续原任务 → 结果记录”，同时验证高风险操作仍需单独授权、吊销与降级会被拦截。
3. **第三方路径**：开放项目会话的元数据检索与一次确认安装，验证拒绝后不绕过、计划变化重新审批、沙箱试运行失败不启用。
4. **学习路径**：从已完成项目任务由执行记录确定性生成草稿，保留血缘与可重复的验证样例，经用户一次确认后受限试运行并在项目启用；不开放常驻扫描和自动发布。
5. **后续扩展**：按实际需求再评估 connector、plugin、远程与 HPC、质量排序和组织策略。

验收以能力缺口任务的完成率、每个成功任务的必要打断次数、失败后恢复成功率及结果记录完整性为主。必测场景包括官网未签名内容不能自动安装、未审查的签名内容仍需确认、第三方拒绝后不绕过、学习草稿不能提前运行、来源删除后草稿失效、升级影响提示及历史结果版本提醒、敏感数据跨工具与模型服务不外泄、停止或恢复不重复远端提交。安装量、创建量和调用量只作诊断指标；另设反向指标：自动安装能力在后续任务中的复用率（识别目录膨胀），以及安装后被停用、回滚或降级的比例（信任判定的早期信号）。

## 10. 待解决的实现问题
