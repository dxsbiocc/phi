# Managed installation for local MCP connectors

Status: first phase implemented (2026-10-09); Docker and explicit source-build adapters remain future work. JavaScript uses Bun by default after the user's steering, with explicit Node runtime compatibility.
Date: 2026-10-09

## Problem and existing foundation

Phi already distributes signed MCP content packages, resolves stdio commands inside
managed environments, sanitizes launch variables, builds environments from locks,
and tracks connector setup and tool discovery. Python and TypeScript connectors
also need reproducible application installation and ownership of every artifact.

BioMCP previously referenced the shared `phi:python@1` environment and downloaded
its binary through a package-local Python launcher. BioMCP1.1.0 now declares the
pinned native executable directly. Phi owns its installation, cache, runtime
metadata and cleanup through the common installer.

Keep stdio as the transport. Separate runtime selection and package installation
from the MCP protocol and from the renderer. Reuse the existing package installer,
environment registry, immutable prefixes, setup notifications, and icon pipeline.

## Source, runtime, and installer

The signed Phi package is the distribution unit. PyPI and npm are upstream package
sources; uv and Bun are installation tools. Docker is an execution backend with a
host engine dependency. These responsibilities must be explicit in the contract.

| Backend          | Runtime and source                                 | Reproducibility and entry                                                                                                             |
| ---------------- | -------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| Python / uv      | Phi-managed Python/uv; pinned PyPI wheels          | Private environment, hash-locked full dependency closure; resolve the installed console script                                        |
| JavaScript / Bun | Phi-managed Bun by default; explicit Node override | Signed manifest and frozen bun.lock or imported package-lock.json, package integrity and pinned runtimes; resolve the installed entry |
| Native artifact  | Declared upstream release artifact                 | Platform-specific fixed URL and checksum; install the verified binary into a managed prefix                                           |
| OCI container    | Compatible host Docker engine; registry image      | Image pinned by digest, tracked container identity and stdio launch without a TTY                                                     |
| Source build     | Explicit package-owned build recipe and toolchain  | Pinned source, build inputs and dependencies; never an automatic fallback                                                             |

Implement Python/uv, JavaScript/Bun and native artifacts first. Docker follows as a
separate host execution adapter. Bun can run a declared TypeScript entry; packages
requiring Node must ship compatible JavaScript. Dependency build scripts are disabled;
source compilation requires a future explicit build adapter.

Python installation must not modify the shared base environment. Use its interpreter
to provision a package-private environment. Do not use a user's global uv tools or
unversioned uvx resolution as the installed connector. This phase installs verified
wheels from a complete hashed requirements lock; project/source installation is deferred.

JavaScript installation uses managed Bun with frozen native Bun or imported npm locks.
Bun is the default runtime; a package can explicitly require managed Node. Runtime
artifacts may be declared with exact version/platform digests. Dependency scripts are
disabled and compiler/native build requirements are rejected. The initial offline cache
adapter is tested with Bun1.3.14; unknown cache ABI versions fail closed.

The connector package chooses its supported backend and platform variants. The
normal Add flow should not ask users to choose an installation tool. Unsupported
platforms remain unavailable; they do not silently switch to source compilation.

## Contract changes

Add a versioned declarative installation descriptor to the environment/package
contracts. Specify backend, upstream package and version, runtime reference or
version constraint, lock artifact, supported platforms, and launch entry. Runtime
configuration generated by Phi must contain resolved paths, never floating package
names or user-supplied installation commands.

The current connector contract rejects unknown keys. Introduce the descriptor with
schema validation, a documented contract revision, and `minAppVersion` for the
first supporting application release. Keep existing `environment`, `command`, and
`args` connectors valid during migration. Container execution needs its own
discriminated contract branch rather than a fictitious conda environment.

## Ownership and lifecycle

Use existing `~/.phi/packages/mcp/<id>/<version>/` directories for signed content and
`~/.phi/runtime/envs/<envId>/` for installed runtimes and application dependencies.
Provider caches belong to `~/.phi/runtime/cache/<envId>/applications/` and are removed
with that environment. Shared provider caches are deferred.
The renderer and package launch scripts must not download or install software.

Environment identity includes the runtime identity, platform, backend, upstream
package version, lock digest and installation inputs. Record executable paths,
artifact digests and resolved dependency versions in managed metadata.

The installer performs this sequence:

1. Validate the signed package, compatibility, installation descriptor and locks.
2. Acquire the installation lock and fetch only the pinned required artifacts.
3. Build a separate versioned environment from the staged signed package; keep the existing active version usable.
4. Mark the built prefix ready and immutable, verify installed versions/executables, and run a bounded MCP initialize/tools probe against the staged package.
5. Check signed source bytes again, then switch the active package/configuration only after successful verification.
6. Release the installation lock and publish success, failure or cancellation.

Persist operation identity and phase so an application restart can identify an
interrupted installation. Reuse the current setup UI for file acquisition,
installation, environment preparation, startup verification and explicit retry.
Report percentages only when actual download byte totals are known.

Upgrades create a new prefix and preserve enablement. Failure leaves the previous
working version active. Running sessions retain their environment leases until
they finish; cleanup must not delete their executable or dependencies.

Uninstall removes connector configuration and releases its environment references.
Garbage collection removes unreferenced managed prefixes and owned cached artifacts.
Container cleanup applies only to Phi-tracked containers and images; never to
unrelated user containers. Shared runtime bases remain while other consumers use them.

## BioMCP migration and icon delivery

BioMCP1.1.0 uses the native-artifact backend to extract the pinned platform binary
from the published `biomcp-cli` wheel. Installation resolves its `biomcp` executable;
stdio launches it with `serve`. The Python launcher and first-launch downloader are
removed. Installed legacy launcher packages retain compatibility until upgraded.
Any cleanup of their old separate cache must target only verified Phi-owned paths.

Icons continue to live in the content repository:
`phi-packages/resources/connectors/biomcp/icon.png`. BioMCP1.1.0 source includes the icon and native managed environment.
Delivery requires committing and pushing the source, then
building and publishing the signed catalog assets and finally the catalog index and
signature. A source push and a catalog release are distinct steps. The installed
package and catalog icon sidecar both retain the verified image; no app-owned
BioMCP branding fallback is added.

## Acceptance checks

- Python, Bun/default and explicit Node connectors install into owned private prefixes and expose real tools.
- Cache hits perform no new package resolution; launch works offline when artifacts exist.
- Locks, hashes and runtime changes produce the correct distinct environment identity.
- Install failure, interruption, retry and upgrade rollback preserve the active version.
- Concurrent installation is serialized; closing a dialog does not cancel or lose status.
- Active sessions prevent environment deletion; uninstall and GC clean owned artifacts.
- Existing remote HTTP and legacy managed stdio connectors keep their behavior.
- BioMCP launches without a first-run downloader and its icon appears from the signed catalog.

## Implementation boundaries

Application adapters live in `src/main/agent/envs/applications/`; package pre-activation
and deferred source cleanup live in small modules under `src/main/agent/packages/`.
Transport ownership is isolated in `omp/owned-stdio-transports.ts`. The existing
environment registry, locking, immutable prefixes and setup display are reused.

The large legacy application entry and OMP worker retain only integration wiring in
this increment. Splitting their unrelated responsibilities would mix the installation
change with a broad migration; that architecture debt remains outside this first phase.
The cohesive environment builder stays below600lines, and all new adapter modules
stay below600lines. No package dependency was added to Phi.
