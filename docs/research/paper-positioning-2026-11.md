## 一、三个基准告诉我们什么

### BixBench3：研究级任务，最强模型不到一半

- 20 个任务，取自已发表研究，138 个评分产物。转录组 16 个、表观组 6 个、蛋白组 2 个、基因组 1 个、微生物组 1 个，其中 6 个为多组学。
- 原始数据平均 67 GB（7 至 241 GB）。环境为 32 vCPU、128 GB 内存、无 GPU 的容器，限时 24 小时、5000 条消息。
- 提示给出研究目标、方法指引（工具、参数、对比、过滤条件）和产物的路径与格式。它考的是**按指定方案执行**，不是选择做什么分析。
- 评分完全程序化：产物分数达到 0.80 算通过，任务分数为通过产物的比例。
- 结果：13 个模型中最高 0.48（GPT 5.6 Sol），Kimi K3 0.47，GLM 5.2 与 Claude Opus 4.8 均为 0.46。
- 全部使用同一个通用 ReAct 循环（Inspect AI），**没有任何专用运行框架的结果**。
- 失败规律：
  - 数据越大越差：小于 50 GB 为 0.37，大于 100 GB 降到 0.10。
  - 链条越长越差：深度 3 以上为 0.24，六个模型显著下降。
  - 低分运行中"过早结束"和"重复重试循环"分别富集约 2.0 倍和 2.2 倍。
  - 作者推测早期错误沿长链累积，但未做验证。
- 成本：每次尝试平均 6.8 小时、1.02 亿 token、43 美元；最贵一次 525 美元。

### BioAgent Bench：流程能跑完，但不查输入

- 10 个小任务（差异表达、变异检测、宏基因组、单细胞等），限 4 小时、48 GB 内存。
- 前沿模型完成率超过 90%，开源权重模型最低约 65%。
- 稳健性测试只用 GPT-5.2 加 Codex CLI，每个条件跑一次：
  - 损坏输入：10 个任务中 3 个未发现；另有 4 个发现了却继续跑完。
  - 诱饵文件：2 个任务把错误文件用进了流程。
  - 提示加长：完成步骤平均减少 28%。
- 同一任务重复四次，结果的平均 Jaccard 相似度只有 0.43。
- 局限：评分由 LLM 完成，且"重完成证据、轻数值准确";稳健性结论作者自称只是"提示性的"。

### scBench-Long：同一模型换框架，结果差很多

- 21 个评测、17 个模型与框架组合、1068 条完成轨迹，以最终结构化答案的确定性判定为准。
- 最高为 Claude Opus 4.8 加 Claude Code，16/63（25.4%）。同一模型换成 PI 框架为 13/63。GPT-5.4 在 PI 上 6/63，在 Codex 上 2/63。
- 失败主要是科学推理问题：用熟悉的先验代替数据、把丰度当重要性、把关联当机制、只看单一模态。
- 任务和框架代码是否公开、第三方系统能否参评，博文未说明。

## 二、对 Phi 的含义

1. **运行框架本身可以是论文贡献。** scBench-Long 显示框架影响明显，BixBench3 则完全没有专用框架的数据。同一模型下"专用框架对通用 ReAct 循环"是一个空着的对照。
2. **公开的失败模式与 Phi 已有或计划中的机制对应。**

| 公开失败模式 | 对应机制 | Phi 现状（依据既有文档，未重新核对代码） |
| --- | --- | --- |
| 过早结束、重复重试 | 计划执行、任务总账、验收关卡、重试预算 | 有计划执行和 acceptance 字段；模型自报完成尚不能替代产物检查 |
| 大数据量下崩溃 | 长作业在 HPC 上运行，完成后可靠回流 | 远程链路已实跑通过；事件回流部分状态仍在内存 |
| 长链误差累积 | 每步产物校验后才解除下游依赖 | 未实现 |
| 不查损坏输入、误用诱饵 | 输入完整性检查、文件来源确认 | 未实现 |
| 重复运行结果不一致 | 用固定版本的社区流程代替临场写代码 | wrapper 路线已有 |

3. **事件驱动方案中只有一部分有证据支撑。** 任务总账、持久执行、成果验收直接对应上表。非阻塞输入、注意力收件箱、跨渠道、常驻宿主、小模型训练在这些基准中没有任何对应的得分点。
4. **科学推理类失败不是工程能解决的。** scBench-Long 的四类失败靠验收关卡帮不上多少，不应在论文中承诺。

## 三、与 Autopipe 的差异

Autopipe 一栏依据源码提交 `9ad7d06`。仓库为 BSD-3-Clause，Rust 加 Tauri，创建于 2026-02，核对时 0 星。

| 维度 | Autopipe（源码） | Phi |
| --- | --- | --- |
| 智能体 | 没有自有循环，是一个约 35 个工具的 MCP 服务，由 Claude、Gemini 等外部客户端驱动 | 自有内核、计划执行、专用子智能体 |
| 流程来源 | LLM 生成 Snakemake 流程、Dockerfile、配置和 RO-Crate 元数据；可从注册表下载或派生 | 封装已验证的 nf-core 流程 |
| nf-core | 只能写在 Snakefile 规则里，以 `nextflow run -profile docker` 调用，并需挂载宿主 Docker 套接字 | 一等公民，由 wrapper 子智能体直接运行 |
| 执行方式 | 经 SSH 在服务器上 `nohup docker run`；另可自动开通 AWS EC2 并挂载 S3 | SSH/HPC，conda，离线计算节点已实测 |
| 作业调度器 | 源码中没有 Slurm、sbatch、qsub 的任何出现 | 已支持集群 |
| 无 Docker 环境 | 不支持；Singularity、Apptainer 没有实现 | 支持 |
| 长作业 | 后台容器加轮询状态；检查退出码和内存溢出；失败后保留输出，靠 Snakemake `--rerun-incomplete` 续跑 | 有计划执行和回流；持久化待补 |
| 校验 | 目录结构校验、源码一致性检查、Snakemake 试运行、注册表安全扫描；**没有对输出结果正确性的检查** | 计划中 |
| 凭据 | SSH 支持密码登录，密码字段存在配置里（是否加密未核对） | 一次性密码引导生成密钥，智能体不接触凭据 |
| 评测 | 仓库内没有任何基准或评测代码；论文中是否有未读到 | 待做 |

结论：

- **两者定位不同。** Autopipe 是"让通用聊天助手生成并分享流程"的工具层；Phi 是带自有智能体的端到端分析系统。它不是 Phi 论文的直接对照对象，但必须在相关工作中引用并说明区别。
- **"桌面应用加注册表加可重跑流程"已被占位**，Phi 不能以此作为新颖性。
- **Phi 可辩护的差异有三点**：能在只有调度器、没有 Docker 的真实集群上运行；直接复用已验证的社区流程而不是每次生成；有结果验收和定量评测（后两项待做）。
- Autopipe 值得借鉴的做法：下载流程时固定到具体提交并要求逐文件审阅、RO-Crate 元数据、内置结果查看器。

## 四、推荐的论文论点

**主张**：在用户自己的计算环境上，一个带已验证流程、验收关卡和可恢复执行的运行框架，能在同一底座模型下显著提高研究级组学任务的完成率和正确率，并降低成本。

支撑实验，按性价比排序：

1. **BioAgent Bench 稳健性复测（先做）。** 任务小、便宜。原文每个条件只跑一次，Phi 可多次重复并报告：损坏输入检出率、检出后是否停止、诱饵误用率、重复运行一致性。这是输入校验功能的直接证据。
2. **BixBench3 主结果。** 同一模型下比较通用 ReAct 循环与 Phi。重点报告大于 100 GB 和深度 3 以上两个子集，这是现有系统最弱的地方。
3. **消融。** 分别关闭 wrapper、验收关卡、计划执行，观察各自贡献。
4. **真实 HPC 案例。** 两到三个在离线集群上从原始数据做到结果的完整案例，报告墙钟时间、人工干预次数和复现性。
5. scBench-Long 视任务是否公开再定，不作为主结果。

## 五、前置条件与成本

- **无界面批量运行。** 三个基准都在容器或沙箱里驱动智能体，Phi 目前是桌面应用。没有这项能力，任何评测都做不了。这是第一项工程任务。
- **BixBench3 的费用。** 按论文的平均值估算，一个模型跑完 20 个任务约 860 美元；四组消融各重复三次约一万美元。这是粗略估算，开跑前应先用两三个任务实测。
- **参评规则。** BixBench3 论文没有说明自定义框架如何提交，需要查其代码仓库或联系作者。
- **计算资源。** BixBench3 要求 32 核、128 GB 内存、500 GB 磁盘、单任务最长 24 小时。

## 六、功能优先级

| 顺序 | 工作 | 理由 |
| --- | --- | --- |
| 1 | 无界面批量运行 | 所有评测的前提 |
| 2 | 输入完整性检查与产物验收 | 对应 BioAgent Bench 稳健性和 BixBench3 误差累积 |
| 3 | 任务总账与长作业可靠回流 | 对应过早结束、重试循环、大数据量失败 |
| 4 | 按评测失败项补插件 | BixBench3 中转录组占 16/20,表观组 6/20,先保证这两类 |
| 暂缓 | 非阻塞输入、注意力收件箱、跨渠道、常驻宿主、模型训练 | 无对应得分点，留给产品路线 |

第 1 至 3 项与事件驱动研究文档中"当前增量"的持久收件、任务身份部分重合，可以合并设计。

## 七、风险与未决问题

- Autopipe 论文全文未读。源码显示它不支持调度器，也没有评测代码；但如果论文正文里有定量评测，第三节的"评测"一行需要改写。
- BixBench3 的方法指引写在提示里，wrapper 的自由度有限：若指定的工具或参数与 nf-core 流程默认值不同，分数可能反而下降。需要先用两三个任务试跑确认。
- 基准分数随新模型快速上升。论文应强调"同一模型下框架带来的增量",而不是绝对分数。
- 目标期刊未定。方法类期刊看重基准与消融；应用类期刊更看重真实案例和可用性。
- 表中 Phi 现状一栏依据既有文档和记录，未在本次重新核对代码。
