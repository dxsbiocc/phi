## 5. 发现与疑点

### 5.1 已确认发现

1. **worker 不是“约 50 个方法”**：`src/main/agent/engine/in-process/main.ts:51-179` 实际有 **62 个 `case` 分支**；计划写“约 60”更接近事实。
2. **`PhiEngine` 有 64 个 callable member**：含 optional diagnostic/control（`hasActiveAgentRuns`、`interruption`、`resourceOwner`、`wait`）、订阅、host register 与 `stop`。账本按用户能力聚合，不强迫“一方法一行”；映射见第 6 节。
3. **旧评估的远端 `agentRuns.start`“完全不支持”已过时**：基线已有持久 UUID、feature gate、host-start command 与测试（PL04），但仍应记“在途”，不能记成普遍已交付。
4. **远端计划不是简单缺少本地两个扩展**：当前使用 `facade-plan-review-tool`、`rpc-plan-policy`、签名 result/phase 的等价实现；`SessionRoutingEngine.enterPlanMode` 仍拒绝 owner，说明公共入口尚未统一。
5. **远端桌面工具面已很宽**：Browser、Notebook、Wrapper、Library、Web search、MCP、项目记忆、环境、Skills 都有真实 adapter；但 `capability_*` 三工具被最终 allowlist 过滤，不能因 builder 存在就写“已交付”。
6. **远端 read 限制仍是硬缺口**：`rpc-entry.ts` 注释仍写“before R5”，明确阻止 PDF/Office/图片/目录/`~`/selector；这不是可用“远程环境不同”搪塞的差异。
7. **`noTools` 要分两件事**：远端 facade 的 `PhiSessionCreateParams.noTools` 确实拒绝；但标题、人设、Notebook 代码、终端草稿这些用户能力仍由桌面辅助会话提供，属于明确保留项，不应迁成第二套主会话内核。
8. **远端 agent 能力受环境变量控制**：`PHI_REMOTE_OMP_AGENTS` 未设置时 definitions 为空；RPC child 大量实现/测试存在并不等于默认用户能力存在。
9. **远端图片只有一半一致**：prompt `images` 可用，但 host-tool `recentUserImages` 在 app routing 中恒空；应在 A12/A15 明确验收附件向工具/子任务传递。
10. **代码量已明显高于旧评估**：基线 `engine/rpc/**/*.ts` 为 25,230 行，`engine/phi-extension/**/*.ts` 为 13,160 行；旧评估的“RPC 16.8k”不能再用于 K5 删除预算。

### 5.2 待决问题（9，2026-10-25 已全部决定）

产品负责人于 2026-10-25 采纳 G0 决策单的全部推荐，每条后面的“决定”即结论。

1. `next-action` 是 V1 必须跨本地/SSH 一致的用户行为，还是允许在统一内核后移除？当前计划没有为它单列产品决定。
   **决定**：两端共用：统一内核后同一份扩展两端都加载（K3-2）。
2. `capability_search/install/find_skills` 是否应在 SSH 主会话开放？当前 builder 存在但 allowlist 排除，像遗漏，也可能是未冻结的安全策略。
   **决定**：K3-2 时三项都对远端开放；前提是先实测装完后远端会话能刷新到新资源，做不到就在结果里明确提示重开会话。验证通过前维持排除。安装仍须用户确认来源、版本和依赖。
3. 远端 `PHI_REMOTE_OMP_AGENTS` 何时从环境变量开发开关转为受信产品配置？在此前，子任务应继续记“环境限制”。
   **决定**：K3-1 转为受信产品配置，默认开启 Phi 自带专家，删除环境变量开关。
4. 远端完整 read 的格式转换器放执行主机还是桌面 host？PDF/Office/图片的 CPU/依赖、数据移动与隐私边界需在 K3-2 冻结。
   **决定**：在执行主机上转换（内核里 OMP 原生 read），数据不离开服务器；K3-2 在离线 node3 上实测 Office 转换依赖，缺依赖时明确报出缺什么。
5. Prompt 四个高级参数是否全部属于公共 v1 DTO？尤其 `synthetic/userInitiated` 是业务语义还是 OMP 私有实现细节。
   **决定**：进入 v1 协议，但只作为宿主内部字段：界面层不能直接传，只有宿主里受信的调用方（如自动换模型重试）可以设置。主会话里目前只有本地自动换模型用到（`automatic-model-fallback.ts:101-103`），其余调用方是桌面辅助功能；与 Q9 一起做（K2-3）。
6. 远端 shell jobs 是沿 OMP async job manager 暴露，还是由统一内核自有 job registry？只补 UI 查询会继续形成第二份状态。
   **决定**：沿用 OMP 自带的 async job manager，统一协议只暴露 list/cancel，内核不另建任务注册表（K3-2）。
7. Wrapper 工具本地主要在 `Wrapper` 专家、SSH 当前直接进入主 roster；统一后是否保留这种模型可见性差异，还是统一成专家委派？
   **决定**：统一成本地的专家委派方式，删除远端主会话里的 6 个 Wrapper 工具；依赖 Q3（K3-1、K3-3）。
8. WIP 的 background-job history 是可重建 UI 缓存还是持久权威？必须明确它不能与内核 run/job 终态形成双写。
   **决定**：只做可重建的界面缓存，不作为权威数据；作业最终状态以内核和作业管理器为准，不得双写。由在途功能的作者在实现时确认。
9. （主力审核新增）远端自动模型选择与失败回退：统一内核后补齐（默认，按“必须共用”处理），还是由产品负责人接受为能力差异并写进 A11？
   **决定**：统一内核时补齐（K2-3）：内核的自动重试经“模型访问”接口取可用模型列表，远端由桌面模型代理提供同一份列表；与 Q5 一起做。差异类别维持“必须共用”。
