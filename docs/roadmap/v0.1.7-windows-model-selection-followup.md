## Accepted change: make the acceptance fixture trustworthy

Automatic session-title requests share the model endpoint with chat. Previously
these requests could consume a queued chat reply. A regression demonstrated a
title request receiving `reuse reply` instead of its own response. The fixture now
answers narrowly recognized title requests separately, including the SDK's leading
system reminder. Ordinary quoted text and tool-carrying requests still consume
their scripted reply. This is test infrastructure, not a placeholder product feature.

Independent review found two additional native-protocol cases: tools live in
`context.tools`, and titles must not consume the one-shot held-request trigger.
Both were corrected while preserving the existing specialist-assessment priority.
The native regression timed out before the correction and passed afterward.

The scratch desktop lifecycle driver also incorrectly awaited the entire prompt
before sending stop. It now starts submission asynchronously, waits for the actual
held request, sends stop, joins submission settlement, and requires a
`run_interrupted` terminal event. It checks subsequent session reuse and restart
separately. Earlier failures are retained; they are not retroactively called passes.

Only `scripts/kernel-e2e/harness.ts`, its new regression test and acceptance records
are adopted. The repair reuses existing request parsing and fixture queues, with
no new dependency or production behavior change. The diagnostic lifecycle driver
remains explicitly diagnostic; a successful stop is not tool-process cleanup proof.

## Rejected compatibility candidate

Artifact alignment was checked before interpreting later controls: the old QA16
installation initially retained a previously rejected 45-second ASAR settings chunk.
The matching original executable/ASAR and original kernel were restored there.
Early read-only/full-auth A/B observations with that stale chunk are retained as
same-package diagnostics, not exact-base acceptance. The S2 candidate was installed
separately under QA17, with host/guest hashes checked; it did not replace a user app.

A candidate defaulted Windows x64 Bun children to `BUN_JSC_useJIT=0` and allowed
30 seconds for two SDK-initializing settings reads. Other controls stayed at
15 seconds, caller-specified deadlines won, and kernel hello stayed at 10 seconds.
An actual Windows Node virtual-clock check passed those policy assertions.

Raw worker auth operations passed three fresh interpreter-only runs (15 cycles,
90 requests), whereas the default control faulted in two of three runs. This did
not generalize to desktop operation. Settings and initial chat sometimes passed,
but the full sequence still failed. Main-process spawn observation verified that
both the kernel and worker received `BUN_JSC_useJIT=0`; a missing flag cannot explain
that observed failure. Neither changing the launcher nor the JIT/settings candidate
is accepted as a product repair.

All four candidate source/test files were restored to the base revision. The
rejected patch, package and failed logs remain diagnostic evidence. The separate
QA17 Windows application and trace kernel must not be distributed as release builds.

## Diagnostic boundary, not a product repair

Two separately built diagnostic kernels used synchronous phase-only stderr markers.
Their hashes were verified on Windows before execution. The first failed inside
`requireAvailableModel`, after credential revalidation and catalog refresh, before
entering the SDK model mutation. The finer trace completed `inCatalog` and printed
`registryFind.before`, then exited `0xC0000005` without `registryFind.after`.
That run places the native failure at the SDK `modelRegistry.find(...)` call boundary.
It does not identify the failing native instruction or prove a universal root cause.
The same test's first selection had completed the entire SDK/setModel/snapshot path.

The source instrumentation was automatically restored after each build; a subsequent
source diff confirmed no diagnostic code remained. These kernels live only in a
separate QA17 diagnostic directory. Their 7,966/9,577 ms hello measurements are
instrumented-build observations, not release startup performance results. No timeout
was relaxed. A native Windows x64 comparison and, if reproduced, native crash-stack
analysis are the next discriminating checks; bypassing the SDK lookup is not a fix.

## Release gates and required environments

- The Windows native process fault remains unresolved. Complete desktop reuse and
  restart acceptance after a verified fix; do not infer it from direct-kernel passes.
- Run the same minimal reproducer and exact reviewed package on **native Windows
  x64** (PC, ordinary x64 VM or CI), using a test account and writable directory.
  This distinguishes supported-target failure from x64-on-ARM compatibility effects;
  the current evidence does not establish which applies.
- Windows first-use long-path handling and VC-runtime redistribution review remain
  the predecessor report's gates. This continuation leaves `LongPathsEnabled=0`.
- WSL checks require Windows with an actual WSL2 distribution and writable test
  directory. The supplied VM has no distribution and nested virtualization is disabled.
- Linux release acceptance requires native Linux x64 with a normal test account,
  writable directory and the declared package sources/cache. A graphical session is
  needed for AppImage/deb installation and desktop Notebook/cancel/restart checks.
  Existing translated-container diagnostics are not a Linux desktop pass.
- Real SSH/network-loss and remote Notebook/Nextflow checks require an authorized
  connection alias and writable remote test directory; scheduler access is needed
  only for an HPC claim. No password needs to be sent in chat.
- Exact-commit release automation and exhausted-quota scientific model repeatability
  remain separate gaps. Offline fixture results do not establish model quality.
