## Confirmed failures and changes

### Missing Windows runtime DLLs

The pinned micromamba EXE failed even on `--version`, before producing output:
`0xC0000135` / `3221225781`. Its SHA256 matched the manifest. Its PE import table
requires `MSVCP140.dll`, `VCRUNTIME140.dll` and `VCRUNTIME140_1.dll`; this VM has no
system VC runtime. The same EXE immediately returned 2.9.0 with exit 0 after those
three files were placed beside it. No system redistributable was installed.

The fetcher now obtains these existing Windows-lock dependencies from the pinned
`vc14_runtime-14.51.36247-habf1de7_42.conda` archive, verifies the archive and all six
selected DLL/licence files, and repairs absent or changed files even when the EXE is
already cached. All member hashes are checked before writing destinations. Scratch
files are removed on failure and success; the archive is not shipped accidentally.
The packaging gate now rejects missing or corrupt sidecars and missing licence files.
No new project dependency or scientific lock version was introduced.

Root rejected the initial custom tar-parser/fallback draft: `tar -xOf` returns member
contents, not a decompressed tar stream. The accepted implementation uses system tar
(or unzip for the outer ZIP with GNU tar), Node's bounded zstd decompression and
selected tar members. Real-archive repair/cache/corruption checks passed on macOS and
Windows Node 22.15.0; a forced ZIP-rejection control exercised the unzip path. The
existing isolated Linux container lacks unzip, so it was not counted as an additional
Linux extraction pass. Linux builders need unzip or a ZIP-capable bsdtar, as with the
existing Bun archive-fetch tooling.

Licence files are preserved, but that is not a redistribution authorisation. The
[Microsoft redistribution documentation](https://learn.microsoft.com/en-us/cpp/windows/redistributing-visual-cpp-files?view=msvc-170)
conditions redistribution on the relevant Visual Studio licence. The package terms
were inspected; public-distribution eligibility has not been established here.

### Desktop stability remains blocked

After the missing cross-build native addon was supplied, the desktop intermittently
failed `settings.webSearch.get` at 15 seconds. The standalone worker took 11,835 ms
on its first settings request and 298 ms on the next. A narrowly scoped 45-second
settings-read policy passed bridge tests but **still failed actual desktop acceptance**.
It was rejected and its source/test changes were restored. The accepted change does
not relax any application deadline or introduce default/placeholder settings.

Further serial runs, after heavy host tests ended and an extra test app was closed,
reported kernel transport closure before a fixture request, or worker exit
`3221225477` (`0xC0000005`) during saving a temporary dummy API key. The same-version
official baseline Bun control passed the settings step but still failed the desktop
prompt. Shortening the isolated user directory did not fix that prompt either.
Standard and baseline Bun each passed 100 standalone SQLite create/WAL/insert/read/
delete/close cycles. This does not reproduce the complete auth mutation path and
cannot rule out a more specific native/runtime defect.

The exact diagnostic kernel independently passed both memory and persistent-session
local-fixture prompts, with EOF shutdown and process exit 0. The memory probe's first
version had an invalid optional host-capability result; that setup warning is retained.
The corrected persistent-session run passed without that warning. These controls
separate the desktop integration failure from a universally broken kernel or basic
SQLite operation. They do **not** establish its root cause or that ARM emulation is
responsible. Native Windows x64 is required for the release-platform comparison;
additional desktop integration diagnosis can still continue on this VM.

The cancellation/restart driver was prepared but did not reach those steps in the
final desktop runs. **Desktop chat cancellation and restart recovery are not passed.**
The earlier single successful desktop chat is retained as a limited, non-repeatable
result and does not override the later failures.

### Windows long-path prerequisite

With `LongPathsEnabled=0`, the full scientific lock failed while validating deep
Jedi cache paths. A shorter root advanced further but failed on deeper ONNX cache
paths. A one-package offline control using the same cached archive failed for both
ordinary and extended-length path arguments. A found deep member was **not** treated
as installation success: both micromamba exit codes were 1.

The EXE declares `longPathAware`; the system policy was disabled. This matches the
[upstream requirements](https://mamba.readthedocs.io/en/latest/user_guide/troubleshooting.html#windows-long-paths)
and the documented [micromamba 2.9 long-path activation regression](https://github.com/mamba-org/mamba/issues/4392).
For one controlled test, the policy was temporarily set to 1, the retained failed
prefix was rebuilt with the same locks, and the host wrapper restored the original
value 0 in `finally`. No reboot or permanent system setting change was made.

Both full environments then became ready. The actual Notebook executed NumPy,
pandas, AnnData and Scanpy normalization with checked numerical output, interpreter
prefix and working directory, and returned `PHI_WINDOWS_NOTEBOOK_OK`.
The first wrapper did not expose a usable child exit code, so a separate fresh server/
kernel run after restoring policy 0 supplied an explicit **exit 0** and additionally
verified interruption of a started long cell, absence of its completion marker,
reuse of the same kernel and kernel process disappearance after session close.
These are real HTTP/WebSocket backend checks with the full Windows scientific lock;
they are not renderer Notebook click-through acceptance.

The current installer does not explain or arrange the long-path prerequisite. A
clean default-policy build still fails; shortening the test directory is not a
product fix. Supported Windows setup needs an explicit prerequisite/check/error
path before general release. Reusing an already-built prefix after restoration is
not evidence that first-time installation works with the policy disabled.
