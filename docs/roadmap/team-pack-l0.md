# 团队包 L0 原型

本文记录团队包 L0 可行性原型的格式、安全边界和后续差距。该原型只验证“管理员发布静态加密资源，成员在管理员离线后仍能拉取、验证、解密和安装”。它没有接入应用启动、UI、IPC 或现有生产来源列表。

## 格式与密钥

- 团队使用 Ed25519 签名密钥。成员预先保存团队公钥指纹；指纹是现有 `registryKeyId` 生成的 16 位十六进制字符串。
- `team.json` 携带完整团队公钥。客户端只有在该公钥计算出的指纹与成员配置一致时才信任它。
- 每名成员使用一对 age X25519 身份和接收方。私钥文件由调用方指定位置，权限固定为 `0600`；原型不读取或写入真实用户目录。
- 每次发布只有一份 age 密文，文件密钥同时封装给当次全部接收成员。公开元数据不保存成员名单或应用层成员标识。
- 签名直接覆盖磁盘上的 JSON 字节；哈希使用 SHA-256。团队签名严格要求签名 `keyId` 等于配置的团队指纹，不接受现有注册表校验中的“未知密钥视为 imported”行为。

静态存储布局如下：

```text
team.json
latest.json
latest.sig.json
releases/<release>/manifest.json
releases/<release>/manifest.sig.json
releases/<release>/payload.age
```

`latest.json` 指向一个单调递增的正整数版本，并包含 `manifest.json` 的 SHA-256。`manifest.json` 记录密文的 SHA-256、字节数、发布时间和可选的已撤回版本列表。发布目录不可覆盖；发布者先在同一文件系统写完临时目录并重命名，最后才更新 `latest.json`。

`publishTeamRelease` 的 `storeDir` 必须是发布者控制的、可备份的规范工作副本，并按追加写语义维护；HTTP、对象存储或其他不可信位置是它的静态镜像和成员拉取面。发布者不能在不可信镜像上删除旧发布后继续复用同一个版本号。若规范副本损坏，应从备份恢复，而不是把镜像中较旧的 `latest.json` 当成发布状态。已经见过某版本的客户端会用本地 manifest 哈希发现同版本异内容，但从未见过旧内容的新客户端无法识别这种发布者侧历史分叉。

`payload.age` 解密后是确定性 tar.gz：

```text
inner.json       # {version: 1, teamId, release}
registry/        # 现有 readRegistry 可读取的软件源
```

客户端按以下顺序拉取：

1. 读取 `team.json` 并核对公钥指纹。
2. 严格验证 `latest.json` 的签名和 `teamId`，再与本地 `{teamKeyId, highestRelease, manifestSha256}` 比较；不同公钥复用同一 `teamId` 会被拒绝，更低版本或同版本不同 manifest 报 `ROLLBACK`。
3. 核对 manifest 哈希、签名、团队和版本。
4. 在 128 MiB 密文上限内下载并核对 payload 大小和哈希。
5. 用成员身份解密。只有在密文哈希已经通过后解密失败，才报 `NOT_A_MEMBER`。
6. 在 256 MiB 解压上限内解析 tar，拒绝绝对路径、`..`、反斜杠、重复路径、链接和非普通文件。
7. 核对 `inner.json` 的团队与版本，在状态目录之外的同文件系统临时目录解包，并用现有 `readRegistry` 验证软件源。
8. 重命名到 `stateDir/<teamId>/<release>/registry`，最后原子写入最高版本状态。

安装不另造逻辑。调用方对拉取结果使用现有 `planInstall` 和 `installPackages`。

## 威胁模型：挡住了什么

- **不可信静态存储读取内容**：没有任一当次成员的 X25519 私钥时，存储运营方、公开镜像访问者和普通非成员不能解密资源。
- **存储篡改**：`latest.json` 和 manifest 的 Ed25519 签名，以及 manifest/payload 的逐层哈希，会拒绝修改、截断或替换。
- **换回旧版本**：客户端持久化最高已见版本，真实签名的旧 `latest.json` 也会因回滚检查被拒绝。
- **跨团队或跨版本搬运密文**：外层签名绑定团队信任根；解密后的 `inner.json` 再绑定 `teamId` 和 `release`。
- **归档路径攻击和简单解压炸弹**：路径、条目类型、重复文件和最大展开字节数均在写盘前受限；无效包不会提交本地最高版本。
- **管理员离线**：发布结果是普通静态文件。发布者进程和签名私钥目录删除后，成员仍可通过目录或 HTTP(S) 存储拉取。
- **跨源跳转与无限下载**：HTTP 实现设置超时和读取上限，只手动跟随有限次同源跳转，404 作为文件不存在处理。

## 威胁模型：没挡住什么

- **已下载内容收不回**：移除成员只影响后续发布。成员已经解密或安装的旧资源不能远程删除。
- **成员私钥泄露**：获得成员 age 私钥的人可以解密所有把该成员列为接收方且仍可取得的版本。L0 没有硬件密钥、轮换或吊销服务。
- **团队签名私钥泄露或丢失**：泄露者可以伪造后续版本；丢失后不能继续以同一信任根发布。L0 只提供文件备份能力，没有管理员恢复或转移协议。
- **已授权发布者作恶**：合法团队签名可以授权恶意资源。现有软件包安装校验保证格式和文件完整性，不证明资源本身安全。
- **成员终端失陷**：恶意软件可读取成员私钥、解密后的注册表和已安装资源。原型不提供终端隔离。
- **扣住新版本**：`latest.json` 没有过期时间。存储只要一直提供成员已见过的那个版本，成员就看不出已有新版本，因此撤回和新版本都可能被扣住，从未拉取过的新成员也可能被给到旧版本。
- **读到一半的指针**：`latest.json` 和 `latest.sig.json` 是两个文件，发布时读取可能短暂得到 `BAD_SIGNATURE`，下次拉取恢复。T1 应合并为一个带签名的文件。
- **可用性攻击**：拉取镜像可以删除文件、持续返回错误、延迟响应或只提供旧版本。客户端会安全失败，但无法让不可用存储恢复；发布者规范副本仍必须由发布者保护和备份。
- **元数据保密**：发布时间、版本号、密文大小、请求时间和大致接收方数量仍可能被观察或推断；团队名称和公钥是明文。
- **流量隐私**：HTTPS 保护传输链路，但 L0 不提供匿名访问、流量填充或私有信息检索。

## 与 T1 的差距

T1 仍需完成以下产品和工程工作：

- 团队创建、加入、成员增删、指纹确认、密钥备份/轮换/恢复和风险提示的 UI 与 IPC。
- 将团队来源接入应用的来源列表、启动生命周期、周期拉取、撤回展示、更新提示和安装交互。
- 为每名成员单独加密和分发模型服务商子 key，并处理吊销、额度和供应商错误；L0 明确不包含模型 key。
- 生产级凭据存储与平台密钥链集成，而不是普通 `0600` 文件。
- 大文件的流式发布、解密和解包，合理的可配置配额，以及对象存储认证、代理和断点恢复。
- 并发发布/拉取锁、崩溃后孤立目录恢复、磁盘耗尽处理和更完整的跨平台原子替换验证。
- 密钥迁移、团队更名、管理员转移、签名私钥丢失后的重建流程，以及成员看到的可解释错误文案。
- 更长时间的兼容性、安全审计和真实存储试点，再决定是否把原型 API 纳入生产路径。

因此，L0 证明核心方案可行并保留可复用代码，但不等同于可面向用户发布的团队功能。
