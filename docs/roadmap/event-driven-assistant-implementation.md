# Phi 事件驱动助手大版本实施计划

日期 2026-11-18。工程基线 `d91cdedc`，应用 `0.1.7`。`v0.2` 是开发代号。发布版本号在兼容和平台验收后确定。依据[架构对照研究](../research/event-driven-assistant-comparison.md)、[内测路线图](internal-beta-implementation.md)和[统一内核计划](phi-kernel-implementation.md)。本计划在独立分支推进，内测修复仍可独立交付。

## 交付目标

- 有运行、审批、压缩或排队时，用户仍可以在原对话中连续发送。持久接收后立即回执，输入框在提交失败时保留可重试内容和同一提交 ID。
- 同一对话可以同时跟踪多个任务。独立任务使用隔离执行会话，依赖任务和访问冲突资源的任务排队。用户可查看、补充或停止指定任务。
- 用户消息、子任务结果及后台任务状态进入同一事件入口。进度直接更新视图。需要判断或交付的事件可以唤醒助手，每个结果的交付可去重和恢复。
- 后台任务面板显示任务归属、状态、阻塞原因、证据和详情。右上角优先提示要处理的事项，其次显示运行和排队数量。两个视图和聊天使用同一权威状态。

## 状态与所有权

| 概念 | 身份与所有权                                                                                                    | 状态约束                                                                                                           |
| ---- | --------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| 事件 | `eventId`、来源及来源去重键、项目/对话归属、持久顺序。桌面主进程接收会话消息和宿主事件，复用内核/生产者原有回执 | 确认接收前落盘。重投返回原回执。来源冲突报告错误。消费收据和产生的工作同时持久化                                   |
| 任务 | `taskId`、触发事件、目标、依赖和资源要求、修订号。项目与对话身份来自已有可信记录                                | 区分等待分流、排队、执行、等待用户、待验收、待交付、已完成、失败、取消和中断。派生视图可重建                       |
| 执行 | `attemptId` 和现有运行 ID，关联任务修订及执行会话。继续由内核拥有实际运行/审批状态                              | 一次执行会话只允许一个写者。只有当前代次可更新任务。断连或退出后的未知副作用进入核对，无法确认的外部操作不自动重跑 |
| 交付 | 对话、任务或外部渠道的去重身份和交付记录                                                                        | 验收和投递各有结果。接收记录、任务结果和交付失败均可单独追踪                                                       |

现有内核还支持 SSH 执行，桌面调度必须按已绑定的宿主运行。SSH 断线保持既有宽限期和权限边界。登记新任务时不消耗运行名额。并行额度沿用当前上限起步，调度器为用户跟进和状态查询保留服务能力。只有代码确认项目授权、资源访问和依赖满足后才能执行。

## 阶段 0 · 冻结基线和故障夹具

- **E0-A，Codex 负责。** 冻结源码提交、包版本、现有 IPC、数据布局和平台阻塞项。区分内部源码集成、候选包和公开发布。基线记录链接到 [v0.1.7 发布就绪](v0.1.7-offline-release-readiness.md)和[平台验收](v0.1.7-platform-acceptance.md)。
- **E0-B，WorkBuddy 或 Qoder 实现，Codex 验收。** 扩展现有[内核合同测试](../../tests/engine-contract/README.md)和[端到端驱动](../../scripts/kernel-e2e.ts)。加入可控慢模型、重复完成、故障切点和实际状态/进程证据。默认使用脚本模型与临时项目，真实模型和平台验收分别记录。
- **阶段验收。** 切换会话、停止目标运行、审批、自动续接、旧历史、安全退出各有现状用例。故障注入必须证明故障确实触发，超时或跳过不能被记为通过。

基线检查记录：lint、应用类型检查通过。`test:gate` 的并行首跑记录 8,025 项通过、4 项失败、26 项跳过、1 项待办。失败涉及编译内核和远程运行目录检查，两套串行重跑 22 项全部通过。后续候选仍报告这两套首跑结果及串行复现结果。基线没有重新进行平台安装验收。

## 阶段 1 · 持久提交和可见队列

- **E1-A，WorkBuddy 实现，Codex 审查。** 在 `src/main/session-runtime/` 内实现单实例持久收件箱和测试。先固定稳定提交 ID、顺序、原子写入和状态推进。利用现有[原子文件写入](../../src/main/agent/engine/kernel-history/atomic-file.ts)和[内核回执](../../src/kernel/agent-runs/receipt-store.ts)的经验。校验持久化的格式、权限和大小，拒绝损坏数据并提供诊断。达到保留容量时仍可完成及取消已接收项。E1 集成需规定清理后仍保留的去重依据及期限。
- **E1-B，WorkBuddy 或 Qoder 实现，Codex 审查。** 接入主进程 IPC 和[现有 prompt 执行队列](../../src/main/session-runtime/prompt-run-queue.ts)。开通新入口前证明同一数据目录在多窗口、第二实例启动及异常退出时仍只有一个可写进程。在首次发送前取得稳定对话身份，保存需要持久引用的附件后再提交，失败时清理孤儿文件。重新调度前比对当前会话、项目和宿主。领取后启动结果不明时标记中断。明确处理首次创建、窗口重载、会话删除及其数据保留、文件丢失、应用退出和无可用模型。已有消息与新回执通过稳定关联键去重。受支持的旧会话继续可用。
- **E1-C，WorkBuddy 或 Qoder 实现，Codex 验收。** 改造 [聊天提交路径](../../src/renderer/src/features/chat/lib/promptSend.ts)、[排空 Hook](../../src/renderer/src/features/chat/hooks/useQueuedPromptDrain.ts)、[后台任务数据](../../src/renderer/src/features/jobs/hooks/useBackgroundJobsData.ts)和[右上角](../../src/renderer/src/components/app-shell/TopRightControls.tsx)。IPC 快照与增量带版本，漏订阅时重拉。旧队列保留到切换验证完成，再删除重复入口。新界面文字遵循[本地化合同](../architecture/ui-localization.md)。
- **阶段验收。** 在 A 运行且占满执行槽时向同一聊天连续提交 B/C/D，三条均收到接收回执，可切换聊天并关闭再打开窗口。只取消 C，剩余按顺序执行。杀进程后排队项可恢复，领取过的未知执行可核对。重复相同提交、IPC 回执丢失、磁盘写入失败和附件恢复均有端到端证据。编写客观的接收延迟测量与吞吐负载用例。

## 阶段 2 · 任务路由、并行执行和定向控制

- **E2-A，Codex 冻结合同，WorkBuddy 或 Qoder 实现。** 路由优先处理显式任务选择、停止、审批回应和状态请求，其次判断是已有任务补充、新任务或需澄清。模糊输入可调用有界判别。把判别输出当建议，权限、资源和依赖由确定规则校验。任务历史、事件与运行分离，默认只给执行器任务摘要、约束、所需产物和来源。
- **E2-B，WorkBuddy 或 Qoder 实现，Codex 审查。** 复用[子任务注册表](../../src/main/agent/agents/registry.ts)与[计划调度](../../src/main/agent/plan/model/plan-scheduler.ts)。形成跨任务资源约束。只读可共享。同一目标写入、共享 Notebook 内核、浏览器会话和受限外部工具按已识别资源串行。实际工具调用检查声明与授权。资源不明时保守排队，同一全局资源集合按确定顺序获取和释放，排队显示原因。等待用户释放模型执行容量，同时保留业务任务身份。
- **E2-C，WorkBuddy 或 Qoder 实现，Codex 验收。** 用稳定任务 ID 定向补充、暂停或取消，已进入工具执行的补充在安全边界交付。区分停止信号已发出和已证实停止。避免用模型选出的字符串作为跨项目操作目标。
- **阶段验收。** 同一对话内独立任务实际重叠执行，共享写资源的任务不重叠。覆盖文件别名和主机身份、模糊跟进、等待审批期间继续发送、晚到结果、两个聊天连续提交的公平性、停止一个任务不终止其同伴，以及后续确认在饱和时仍能送达。

## 阶段 3 · 后台结果回流和成果验收

- **E3-A，WorkBuddy 或 Qoder 实现，Codex 审查。** 将[现有续接逻辑](../../src/main/agent/agents/run-continue.ts)、[内核子任务回执协调](../../src/kernel/agent-runs/coordinator.ts)及 Wrapper、Shell、计划的完成信号接到持久入口。用生产者回执 ID 与任务代次去重，避免主进程和内核双重续接。需要结论、失败处理或用户决定的事件才消耗模型调用。进度可合并并直接投影。验证重启、通知丢失和订阅重连后可核对，禁止根据日志文本判定成功。
- **E3-B，WorkBuddy 或 Qoder 实现，Codex 验收。** 对接[科学可信计划](scientific-trust-implementation.md)中适用的 T1/T2/T6 合同，引用产物快照和机器验收结果。区分执行完成、验收通过、已交付和待用户审阅。错误产物不解锁依赖。验收始终在产物所属宿主运行。
- **E3-C，WorkBuddy 或 Qoder 实现，Codex 验收。** 后台任务详情展示失败原因、重试资格、待审批/输入、结果引用及验证证据。右上角与主列表共用计数，打开聊天与消除待决状态分开处理。
- **阶段验收。** 断开 Renderer 后完成子任务，重连只出现一次结论或待决事项。崩溃发生在状态落盘前后、消费确认前后或交付前后时，仍能核对一次逻辑交付。取消的任务只更新状态。同一后台事件刷 100 次进度不增加模型调用。缺主产物即使退出码为 0 也不能通过验收。

## 阶段 4 · 内测放量与发布

- **E4-A，Codex 负责，模型可承担独立验证任务。** 先用脚本模型和生产宿主集成，再覆盖真实模型、本地/SSH、原生平台候选。测试旧历史、审批与取消、恢复、容量、网络断开、迟到结果、数据格式升级与回退。回退前检查存在的排队或未决任务，旧版本不可误吞它们。
- **E4-B，Codex 负责。** 开发开关内测，记录录入延迟、队列年龄、重复投递、遗漏唤醒、未知运行和跨项目隔离。确认已有内测闸门与[平台验收](v0.1.7-platform-acceptance.md)的影响，准备可回退候选和证据索引。
- **阶段验收。** 新增功能通过应用入口与可复验故障集；验证过的平台逐一记录。完成队列持久化、后台回流和所有权的高优先级缺陷，审阅各阶段差异，原生平台阻塞关闭后再打发布标签。

## 阶段 5 · 后续里程碑

- **E5-A，触发器。** 先做有明确来源和权限的定时/文件/作业事件，提供幂等键、频率上限、预算、暂停和审计。达到内测后再扩连接器。
- **E5-B，持续运行。** 在现有宿主断线语义之上增加明确选择的常驻模式、独立监督、执行租约与结果核对、凭据边界。桌面退出后持久运行需要单独的运维和真实故障验收。
- **E5-C，跨渠道和经验。** 用独立接入层做用户与项目映射、消息回投和最小权限。先建立用户可控的反馈、项目记忆、离线评测和回滚门槛，再评估训练。具体渠道跟随[协作与移动路线](../design/phi-mobile-companion-design.md)。

E0 与 E1 的夹具/存储可并行。E1-B 依赖 E1-A，E1-C 在 IPC 合同冻结后并行。E2 的资源约束是开放独立写任务的前置，E3 的核对是开放可靠自动续接的前置。E1 到 E4 是大版本核心，E5 为后续里程碑。

## 派工、复用与审查

- 使用 DeepSeek Harness 的 WorkBuddy 或 Qoder 中实际可验证的授权模型。每项任务固定基线、所有权、范围、测试、退出条件与回执。模型在独立工作目录提交候选文件。Codex 维护集成分支、确认调用身份、逐行审阅、补充反例并重新运行测试。模型自报通过仅作诊断记录。
- 复用 Phi 的执行器、审批、回执和状态接口。可适配 DeepSeek 原型 MIT 的事务副作用与交付用例、Rakazo Apache-2.0 的定向补充与回流用例、OpenMuse MIT 的执行租约与通知用例。若移植代码，记录来源提交、文件和许可证声明。Comma 的 AGPL-3.0 代码用于架构对照。详见[复用清单](../research/event-driven-assistant-comparison.md#其他开源项目的具体复用位置)。
- 针对每项候选检查正常路径、失败原子性、幂等与竞态、运行归属、状态跨重启一致性、兼容性和资源清理。集成前运行关联测试、`bun run typecheck`、`bun run lint` 和 `bun run test:gate`。涉及前端边界时执行 `bun run check:architecture`。必须记录未覆盖的平台、外部服务和真实运行场景。
- 除源代码和经过审查的结论外，模型原始输出、会话、凭据和本地论文材料均保留在其原有访问范围。
