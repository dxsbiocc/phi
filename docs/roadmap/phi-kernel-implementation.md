日期：2026-10-24。状态：规划修订，等待用户明确开工；当前只维护计划文档。此前产生的代码改动单独记入 §17，不视为本计划的开工授权或阶段验收。

产品方向已获用户认可：Phi 拥有统一运行时与 RPC，内部复用固定版本 OMP SDK，暂不维护 OMP 源码分叉。人力已确认：**一名主力开发者 + Codex 辅助**。本文给出建议范围、交付节奏与验收门；估算不是已承诺的发布日期。

**当前版本只交付本地与远程统一运行模式、统一业务实现和 UI 解耦。团队包与实验室服务器版、成员管理、资源与环境共享、共享模型和用量管控属于下一个大版本；群聊、任务委托等协作功能更晚。** 本计划仅把下一大版本所需的兼容约束写进当前设计，不提前实施这些产品功能，也不将它们加入当前排期。本文负责当前版本的实施安排，[验收规格](#acceptance-spec)直接收录于本文 §18。下一大版本的产品与交付方向由另一份[个人版与实验室版计划](phi-personal-lab-roadmap.md)管理。现有远程能力、部署、恢复和测试继续复用；旧的[本地 RPC 评估](../architecture/local-rpc-migration-assessment.md)仅作方案与测量输入。

## 1. 项目目的与交付承诺

解决的问题：同一个会话能力目前要分别接入本地 SDK worker 和远程 OMP RPC，导致重复开发、行为差异和验收成本。项目交付后，新增一个会话功能应主要修改一份内核业务代码，再由相同合同测试验证本地与远端。

下一大版本方向仅作兼容背景：个人版、团队包（无服务器）和实验室服务器版共用同一个内核，核心是共享资源、共享模型和用量管控；任务始终由成员用自己的账号执行，实验室服务不替成员执行。群聊、任务委托等协作功能在更后的版本。当前不引入新的账号、空间或任务产品；§4 给出本次必须考虑的兼容约束，§16 说明与另一份产品计划的关系。

当前版本的交付承诺：

1. 本地与 SSH 远程使用同一份 Phi 智能体内核实现，保持当前已交付的交互与能力。
2. 会话、计划、子任务、审批与恢复有唯一执行状态；切换聊天不会打断任务，停止不会影响其他会话。
3. 桌面 UI 通过 Phi 协议使用内核；没有 Electron 的测试客户端也能完成对话、工具执行、审批、取消和恢复。
4. 能力不可用时说明原因；远程操作不转为在本机项目路径执行。
5. 切换失败可以停止扩大试用、回到已验证版本；已产生的历史与成果不会因回退被清空。

“无 UI 运行”指内核不导入 Electron/React，不要求窗口存在；客户端仍可提供模型凭据代理和交互回调。它不等于本阶段已支持脱离所有客户端后持续执行。当前保持现有退出/取消行为，但把连接关闭、用户取消和运行时销毁区分在接口上，避免下个大版本增加服务器生命周期时重写执行逻辑。本版不实现服务器常驻任务。

本项目的 Agent Kernel 与既有 micromamba/Python/R 受管环境运行时是不同概念；不重做环境管理。

## 4. 实现方案与状态归属

建议结构是同一仓库内的模块拆分，不新增独立仓库或微服务体系。路径是拟新增目标，K1 可按现有边界检查做小幅调整，并同步本文。

| 模块（拟新增）                         | 责任                                            | 禁止承担的责任                        |
| -------------------------------------- | ----------------------------------------------- | ------------------------------------- |
| `src/shared/kernel-protocol/`          | Phi 命令/事件 DTO、版本、能力、错误分类         | OMP 对象、窗口对象、可执行函数序列化  |
| `src/kernel/`                          | 会话/run/子任务/计划/审批/历史编排、统一装配    | Electron/React、选中窗口、UI 未读样式 |
| `src/kernel/omp/`                      | 固定 SDK 与内部 API 适配                        | 把 OMP 类型泄漏给客户端               |
| `src/kernel/main.ts`                   | 无 UI 进程入口、协议调度和退出清理              | 公网监听、多租户守护进程              |
| `src/main/agent/engine/kernel-client/` | 本地/SSH 连接、PhiEngine 适配、桌面宿主能力注册 | 再实现计划执行、审批策略或运行终态    |

迁移中按功能搬迁而非先大规模搬目录。每次先锁定行为，抽出该功能，再改两端调用，最后删除被替代实现。新 OMP 导入范围要精确扩展到内核适配模块并有负面检查，不能取消现有引擎边界门。

状态归属：

- 执行所在内核是会话执行状态、run、子任务、审批、计划和执行日志的唯一写者。
- 桌面保留项目/主机目录、用户全局设置、UI 未读/选中状态及远端索引投影；不独立结算执行结果。
- 历史保持现有 Phi session ID 与 OMP journal 关系。每个存储对象明确一位写者；迁移时明确本地清单中哪些字段是权威、哪些是远端投影，避免两端都可写同一状态。
- 模型认证 broker 负责凭据与刷新；本地直连、远端代理是认证/传输适配差异，不允许因此复制会话状态机。内核只依赖“模型访问”接口（选模型、发起请求、取消、报告可用性），不知道背后是直连、客户端代理，还是以后的服务端凭据服务；“模型暂时不可达”（例如客户端断线）是这个接口上一种明确的状态，不是笼统的失败。
- 浏览器、文件揭示等桌面能力通过注册后的 host capability 使用。未注册就返回能力不可用；不在内核模拟成功。
- 大文件、Notebook 内容和工具输出沿既有 artifact/分块传输路径；RPC 承载控制和引用，不把全部二进制塞进每个事件。

协议在 K1 冻结最小 v1：创建/发送/取消/快照/订阅/审批应答/关闭，加能力发现和版本握手。请求携带 session/run/request ID 与运行代次；身份/空间上下文由可信入口构造，预留 conversation/task 映射，不能接收自报角色作为权限；事件有序号；收到请求与最终完成分离。已有 RPC 的完成、撤销、过期代次规则作为回归来源。

**协议不绑定传输**：v1 的帧格式、请求/事件身份和生命周期语义与具体传输分离。本版只实现本机 stdio 与 SSH stdio，但会话、run、审批的身份都不能等同于“这一条连接”或“这一个进程”：连接断开只是失去一个控制者，不等于取消或销毁会话。下一大版本的实验室服务改走经过认证的网络连接时，只新增一个传输适配和可信入口，不改命令/事件语义。K1-1 用负面用例证明协议层不读取 stdio 特有状态（如进程 PID、管道关闭）作为业务判断依据。

**内核生命周期与重连**（2026-10-24 新增）：一个主机共用一个内核之后，如果内核的寿命仍然等于 SSH 的 stdio 连接，那么断线重连时，这台主机上的所有会话都要重启内核、再逐个恢复，"断线不等于取消"也就只停留在纸面上。所以远端改成下面的做法：

- 每个"主机 + OS 用户 + 内核版本"只有一个内核进程。内核监听运行时根目录下一个私有 Unix socket（所在目录权限 0700，只有本 OS 用户能访问），不监听 TCP 端口，因为共享登录节点上的其他用户能连到 127.0.0.1。每次连接还要校验该内核的随机令牌。
- 桌面端通过 `ssh 主机 phi-helper attach` 连接：helper 把 SSH 的 stdio 转接到 socket；内核没在跑时由 helper 拉起，并用文件锁保证同一 OS 用户、同一版本只拉起一个。
- **断线后的宽限期**：连接断开后，内核继续存活一段宽限期（时长在 G1 确定）。宽限期内，正在执行的工具可以跑完；需要客户端才能继续的步骤（经桌面模型代理调模型、等待审批、调用桌面宿主能力）停在明确的"等待客户端"状态，不自动批准、不自动重发。客户端在宽限期内重连后，先对齐快照和可重放事件，再成为唯一的控制者。
- **宽限期满仍没有客户端**：内核按现有退出策略处理，即停止运行、取消待审批，不能证明已停止的记录为 UNKNOWN，然后退出。这不等于"客户端离线后继续无人值守运行"，后者仍属 §2.2 的不做范围。
- **版本不同**：新版本客户端不接管协议不兼容的旧内核。旧内核按宽限期规则自然退出，或者由用户确认后停止。
- **本地**：本地内核仍是桌面端拉起的子进程，走 stdio；桌面端退出时按现有策略停止内核。协议和会话语义与远端完全一样，差别只在传输。
- **下一大版本**：实验室服务器版不替成员执行任务，成员在服务器上的内核仍按本节的模型、以成员自己的 OS 账号运行，客户端照常经 `phi-helper attach` 连接。只有更后的协作版本才可能把宽限期扩展成“服务端持有任务”，届时只需新增传输与可信入口，命令和事件语义不用改。

协议不保证外部副作用“恰好一次”：用持久请求身份、结果核对和 UNKNOWN 状态避免盲目重试。存量连接只有一个控制者；新连接不能同时获得旧连接的写权限。重连先对齐快照和可重放事件，不能重放执行命令。

### 4.2 兼容约束的验收方式

CR1–CR6 通过设计评审、当前调用链检查及已有行为合同验证，不要求实现下个版本的假服务器或虚构成员。每项在对应 K 任务中记录接口位置、当前调用方、未来扩展方式及明确不实施项。

“可扩展”不等于现在建立所有未来字段：只有当前本地/远程统一所需的参数、依赖注入和版本机制才进入代码；未来主体/空间/委托字段可在协议协商下增加。现有审批、远程签名白名单、历史格式和个人体验保持不变。

禁止将个人身份/空间文件、多人任务状态机、实验室能力替身或完整共享资源模型作为本版本放行前置。此前超出范围产生的归属代码仅在 §17 记事实，不能借兼容之名计入本版必须交付。

- G5：现场选择一个小型会话功能，说明唯一实现位置和两端共用的验收；搜索和构建检查证明旧路径不再可达。

产品负责人每个门预留约 30–60 分钟观看演示与确认范围/体验，主力负责提供证据。自动测试绿色与产品验收分别记录，不能互相代替。

### 8.1 S0 预测量（2026-10-24，非 G1 结论）

在本机 macOS arm64 上测过三种进程形态，用的是真实 OMP 18.10.3 和脚本化模型，对话中每轮先读一次文件、再回答。没有接真实提供商，也没有测 Windows。数据会随机器负载波动约 ±20%。脚本和完整方法见[旧评估 §3](../architecture/local-rpc-migration-assessment.md)。

| 形态                                                                        | 新会话就绪                      | 内存                                                                | 4 个活动会话合计  |
| --------------------------------------------------------------------------- | ------------------------------- | ------------------------------------------------------------------- | ----------------- |
| 一个进程共用多个会话（现有 worker 方式）                                    | 约 65 ms（第一个会话约 180 ms） | 只加载 SDK 约 340 MB；1 个会话约 440 MB；之后每多一个会话 +15–25 MB | 约 500 MB（基线） |
| 每会话一个 bun 进程（SDK + 源码，即现在的打包方式）                         | 0.87–1.13 s                     | 每个 550–570 MB                                                     | 约 2.2–2.3 GB     |
| 每会话一个编译单文件（OMP 官方 `omp-darwin-arm64` + Phi 扩展，HOME 已预热） | 0.27–0.31 s                     | 每个 280–310 MB                                                     | 约 1.1–1.2 GB     |

按上表的硬门（4 个活动会话超过 1.5 GiB，或超过基线 2 倍即约 1 GB，都算失败），每会话一个进程的两种形态都会失败。这是 §2.3 默认采用共享内核进程的依据。编译单文件比 bun 跑源码快约 3 倍、内存少约一半，所以 K1-3 优先出编译版。单文件第一次在某个 HOME 下运行时要解出约 94 MB 原生库，多花约 1.2 秒，因此原生库要按版本共享，不能每个会话各解一份。对话本身的内存增长约每轮 1 MB，20 轮约 +25–30 MB，所以内存主要取决于常驻进程数。G1 必须在真实内核入口和真实项目资源上重新测量；本节数据不能代替 G1。

### 8.2 K0-4 编译验证结果（2026-10-25，非 G1 结论）

**结论：通过。** 现有 worker 用 `bun build --compile` 编成 Linux x64 单文件（`bun-linux-x64-baseline` 目标，OMP 18.10.3），在 node3 和 GPU 主机上都用脚本模型跑通了“读文件 → 写文件 → bash”，生产代码零改动。§2.3 的方向不需要调整，G0 中“K0-4 跑通”一项满足。

做法：

- 由 Codex 实现，主力审查代码，并亲自在两台主机上执行。
- 测试用的驱动也编译成单文件，它会校验：工具按“读 → 写 → bash”的顺序执行、工具批准正好 3 次、写出的文件内容正确、bash 输出回到对话、会话正常结束。
- 每台主机跑两轮：第一轮是空 HOME（需要解压原生库），第二轮复用同一个 HOME。
- 远端测试包和结果已从服务器清理。
- spike 代码在分支 `spike/k0-4-kernel-compile`（`scripts/spike/k0-4/`），未提交。

| 主机                                           | 就绪（首次 / 再次） | 新建会话 | 一轮对话 | 常驻内存      | 峰值内存（首次 / 再次） |
| ---------------------------------------------- | ------------------- | -------- | -------- | ------------- | ----------------------- |
| node3（CentOS 7，内核 3.10，glibc 2.17）       | 2.5 s / 1.7 s       | 0.36 s   | 0.6 s    | 约 355 MB     | 1.02 GB / 386 MB        |
| GPU（Ubuntu，内核 5.15，glibc 2.35）           | 3.2 s / 2.3 s       | 0.5 s    | 0.46 s   | 约 370 MB     | 1.03 GB / 398 MB        |
| 本机 macOS arm64（编译版）                     | 2.4 s / 0.7 s       | 0.13 s   | 0.16 s   | 约 512–538 MB | —                       |
| 本机 macOS arm64（对照：bun 跑源码，现有方式） | 1.4 s / 0.73 s      | 0.13 s   | 0.16 s   | 约 480–505 MB | —                       |

- 包体积：Linux 内核单文件 210 MB。原生库以 zstd 压缩嵌在内核里，首次运行时解到 `$HOME/.omp/natives/18.10.3/`。同一个 HOME 下的多个进程共用这一份，第二次运行不会重新解压。
- glibc：内核和两份原生库要求的最高版本都是 `GLIBC_2.17`。原生库另外依赖 `libutil.so.1`，两台主机上都有。
- 编译版与现有方式（bun 直接跑源码）启动速度相同，内存约多 30 MB。编译本身没有带来明显开销。

后续修正（已写入 K1-2、K1-3）：

1. **只解出当前 CPU 需要的那份原生库。** 现在的 Linux 包同时嵌入了 baseline 和 modern 两份原生库，每份 110 MB，首次运行两份都解压。结果是首次运行峰值内存约 1 GB，磁盘多占 110 MB。再次运行峰值不到 400 MB，不受影响。K1-3 改为按 CPU 只嵌入或只解出一份。
2. **降低 worker 的常驻内存。** 本机常驻约 510 MB，S0 测的 OMP 官方单文件约 300 MB。多出来的部分来自 worker 自己加载的模块，不是编译造成的（见上面的对照行）。按一台主机一个共享内核计算，4 个会话约 600 MB，仍在 §8 硬门以内，不阻挡 G0。K1-2 核查启动时加载的模块，能按需加载的改为按需加载。

spike 的限制：OMP 官方构建会生成一张旧版扩展加载表（虚拟模块 `omp-legacy-pi-modules`）。spike 用一张空表代替，并关闭了扩展发现。因此这次没有验证旧版第三方扩展的加载，K1-3 要按官方构建方式正式提供这张表。

## 9. 发布、历史切换与回退

1. **开发期**：新入口只用于一次性项目和合同测试；继续当前发布行为。临时开发开关有负责人和 K5 删除点，不能成为永久双轨。
2. **内部试用**：先限定新建测试会话，再选已备份的当前格式旧会话。一个会话只选择一个运行时和一个写者；不能对真实写入做新旧双跑。
3. **默认切换**：本地与远端分别经过 G4；可先切风险更小的一端，但公开里程碑要同时完成两端才算交付。服务端版本/能力握手通过前不创建可执行会话。
4. **稳定收口**：完成观察期，关闭全部 Sev0/Sev1，再删除旧执行路径和临时开关。保留已验证发行包用于回退，不长期保留两个业务实现。

历史策略默认保留现有 journal 格式，新增 Phi 元数据使用可忽略的伴随文件；不在迁移时原地改写旧 journal。K2-4 对当前本地/SSH 历史各准备普通会话、压缩后会话、工具/子任务会话、失效模型会话、计划执行中断会话样本。

**RPC 时期的远程会话**（2026-10-23 起默认，由服务器上的 `omp --mode rpc` 写入）单列一类样本，按下面的规则映射：

- 会话日志是同一固定 SDK 版本写的 journal，由 Phi 内核直接打开，原件不改写。能否续跑以 A19 的实测为准，不凭"格式相同"推定。
- 桌面 manifest 中的 `runtimeRef`、`runtimeSessionPath`、`runtimeRecoveryError`（解析见 [manifest-file](../../src/main/agent/session/manifest-file.ts)）映射到新内核的会话归属记录。映射前先核对原主机、项目、运行时根目录和会话身份一致，不一致的保持只读。
- 服务器上的写者锁与 `run.lock`（见 [run-guard](../../src/main/agent/engine/rpc/run-guard.ts)）：接管前必须证明旧 OMP 进程已经停止或已被合法接管，沿用现有 TERM→KILL 接管规则；不能证明时显示 interrupted/UNKNOWN，不自动续跑。
- 执行授权租约、bootstrap 证明、扩展包哈希这类 RPC 专用状态不迁移，只作为只读的诊断记录保留。新内核按自己的协议重新建立执行身份。
- 更早的旧版 SSH 会话（没有 `runtimeRef`）继续只读，不在本次映射。

原始备份、目标引用、迁移版本和操作完成状态组成迁移记录；中途退出可再次核对后完成。

回退不等于回滚用户产生的文件副作用：这些内容必须保留并可见。已有新版本写入只有经过旧版本兼容性证明才能继续交给旧版本执行；不能兼容的会话保留可读历史与成果，在修复前暂停续跑，不把历史重置。此策略与停写/回退步骤必须在 G2 演练，并在 G4 的最终候选复验。

远端的回退基线是当前已验证的 OMP RPC 发布路径，不能重新引入此前已删除的“在桌面执行远程 Agent 工具”旧路径。回退使用已验证发行包和会话归属记录；不为回退永久保留两份业务源码。

Sev0：数据丢失、越权/错误主机执行、跨会话污染。Sev1：核心会话不可用、任务重复启动、无法停止且状态误报、历史恢复阻断、超过硬资源预算。二者阻止默认切换；普通体验问题记录负责人和修复点。

## 12. 与现有路线图的关系及完成定义

[内测路线图](internal-beta-implementation.md)仍以可靠的本地工作台为成功标准。K0/K1 可以先推进，不改变默认执行路径；K4 大切换安排在内测候选稳定窗口。个人版/实验室版及其协作功能明确放入下一大版本。本版只有统一内核及兼容设计检查，不因长期方向提前开启群聊、成员管理、身份存储或服务器产品建设。

## 13. 方案决策记录

决定：建立 Phi 自有智能体内核与协议，复用固定 OMP SDK，并通过逐项迁移删除两套主会话实现。

驱动：减少重复实现；让 UI 和执行位置独立；保留现有行为与上游模型能力。

考虑过的替代：只统一到 OMP CLI RPC，短期改动较小但不能充分解决桌面宿主耦合与业务协议控制；完整抽取 OMP 源码，可以修改底层但引入上游同步、原生发行与兼容维护。本项目选择中间路径。

否决"只统一到 OMP CLI RPC"的实测与代码依据（2026-10-24，见[旧评估](../architecture/local-rpc-migration-assessment.md)和 §8.1）：

- **一个进程只能跑一个会话**。OMP CLI RPC 的会话、连接、进程生命周期是绑在一起的。每会话一个编译单文件，4 个会话约 1.1–1.2 GB，超过基线的 2 倍，过不了 §8 的硬门。
- **Phi 业务逻辑仍是两份**：一份在 OMP 扩展里，一份在桌面驱动层。远程驱动层（`engine/rpc/`）已经约 16.8k 行，远程扩展约 4.5k 行。本地已有的能力在 RPC 下全部要重写：计划模式、主进程启动子任务、prompt 参数、后台 shell、历史分叉、子任务 `max` 思考级别、完整的原生 `read`。
- **不符合下一大版本的要求**：服务器持有任务、多客户端订阅、审批收件箱、可信入口里的调用者上下文（CR1–CR6）都没有协议位置。
- **能保留的经验**：执行授权、写者锁、恢复、部署与故障用例作为协议无关部分复用（§3）。

代价也要记下来：对 OMP 的依赖从"RPC 协议"变成"SDK 接口"。SDK 内部接口在升级时可能变化更多，所以对 OMP 的直接调用必须全部收进 `src/kernel/omp/` 适配层，升级时只改这一层，再跑一遍合同测试。

代价：需要维护 Phi 协议版本、运行包和 SDK 适配；不会消除平台适配和多环境测试。进程共享与内存收益必须以测量证明。

后续：只有具体 SDK 限制持续阻塞、局部适配无法解决时才提出模块级抽取；团队包、实验室服务器版、共享环境与共享模型等下一大版本需求由[个人版、团队包与实验室服务器版计划](phi-personal-lab-roadmap.md)细化；本文只维护当前统一 RPC 范围与兼容约束。
