## Finding

`modelRegistry.find` is an observed JavaScript boundary, **not an established root
cause**. The terminal native failure is now substantially better understood:
Bun's embedded Windows crash-handling path repeatedly faults, exhausts a thread's
stack and ends with `0xC0000005`. The original triggering exception, and whether it
also occurs on native Windows x64, remain unresolved.

The existing machine is Windows 11 ARM64 build 26300.9711 under Parallels, executing
x64 Node/Bun/kernel binaries. These results cannot establish native Windows x64
behavior. Neither the timing-sensitive passes nor the independent registry test
is a release acceptance pass.

## Native evidence

The original kernel SHA256 stayed
`9decd52552b006551cb01ed197e9371d1ef7dfbfbafa0e2618eec37ebf413bb8`;
its native addon stayed
`075fb5a0866a6f02a22c58e004f05131ab288b980514dfe6b64e29bd527c990a`.
The ordinary Bun executable stayed
`0187f68d843f825a72ada4a7eca60db896ed753759a7f8252edcd31ac1bf1b9c`.

One independently captured dump contains:

- Faulting thread 12560, instruction pointer `phi-kernel.exe + 0x1fc0`.
- `RSP = 0x6870600980`; the failing write is `0x6870600978`, exactly `RSP - 8`.
- The instruction at `+0x1fc0` is a `call`, whose return-address push explains that
  write. The stack buffer passed to the called routine is within its allocated frame.
- The dump's captured stack begins at `0x6870601000`; the fault is below it.
  `VirtualQueryEx` independently reports the fault page as `MEM_RESERVE`, not a
  committed writable page. This establishes terminal stack exhaustion in this run.
- A scan found 3,039 exception-record-shaped structures: 3,037 null-read records
  at `+0x1fd4`, one late stack-overflow record at `+0x1fc0`, and an older NTDLL
  access-violation candidate. Most repeated structures are spaced 6,208 bytes apart.
- Disassembly at `+0x1fd4` reads a TLS slot; the caller at `+0x3da0` dispatches
  Windows exception codes into the crash handler. This is consistent with failure
  while reading Bun's thread-local panic guard, followed by recursive handling.

The [Bun 1.3.14 crash-handler source](https://github.com/oven-sh/bun/blob/bun-v1.3.14/src/crash_handler/crash_handler.zig)
contains that thread-local guard and Windows exception dispatch. This supports the
mechanism interpretation; it does not identify what triggered the first exception.
The scan is **not a validated unwind**, and matching the executable's default stack
size does **not** identify the crashing thread as the main thread.

The oldest candidate record points to `ntdll.dll + 0x18c580`, reading
`0x68e2ffe4c0`. It is a candidate recovered from memory, not a directly observed
first-chance event. An upstream [Tailwind discussion](https://github.com/tailwindlabs/tailwindcss/issues/20470)
contains a similar Bun 1.3.14/x64-on-ARM crash signature, including the same handler
RVAs. That user's AI-assisted analysis is an analogy only; it does not establish
Phi's root cause or justify importing their unrelated addon fix.

A separate one-shot breakpoint experiment attempted to capture entry to the
handler. Under this environment the breakpoint itself was redispatched through
exception handling before the observer received it. Its captured context chain
contains our breakpoint and stack overflow. The probe restored the code byte and
intentionally terminated its own isolated process with `0xB0A`; this is **not** an
additional natural product crash and did not settle the initial-exception question.
No executable on disk was patched.

## Review decisions and integrity

The supervising review corrected several DSH draft defects and overclaims:

- JIT flags must be supplied before starting Bun, not changed after importing the SDK.
- Read-only settings and a reduced lookup loop are not exact full-kernel controls.
- Git diffs omit ignored dependencies; the diagnostic builder now saves a complete
  temporary diff and verifies byte-for-byte restoration of all three touched files.
- Second chance does not mean non-continuable; an attach breakpoint is expected;
  a stack address's visual shape does not establish corruption.
- Importing a stack-guarantee API does not prove it executed; missing first-chance
  events do not prove that an older memory record is stale.
- Failure inside the runtime's handler does not exonerate every earlier native
  operation. No native addon removal, same-model shortcut or speculative timeout/JIT
  policy was accepted as a repair.

The diagnostic trace produced large logs and changed timing. Its isolated success
was followed by failures and is retained only as diagnostic evidence. Initial
preparation failures (missing cache/output/addon placement) were corrected and kept
separately; they were not counted as runtime test results. A test driver that left
its scenario waiter alive after failure was corrected to close it in `finally`.
Its earlier residual process was identified by exact test command and cleaned up.

Product sources and temporary SDK instrumentation are restored, with matching
before/after hashes. There is no product-code change to run the previous 66-check
suite against; that earlier result remains historical. This continuation checks
artifact hashes, actual Windows execution, diagnostic restoration, ledger integrity
and documentation formatting. User-owned roadmap and research edits remain intact.
