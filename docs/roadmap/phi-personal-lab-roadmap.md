# PHI 个人版、团队包与实验室服务器版：下一大版本产品及交付计划

日期：2026-10-24（当日按用户的实验室构想重写）。状态：产品规划，未授权开工。人力假设：一名主力开发者 + Codex 辅助。

本主题使用三份文档：本文负责下一大版本的产品与项目安排；[本地与远程统一 RPC 计划](phi-kernel-implementation.md)负责当前版本的内核统一、兼容设计和验收；[K0-1 能力账本](phi-kernel-capability-ledger.md)记录当前每项能力的现状与归属，随任务更新。本文不能扩大当前版本的实施范围或工期。所需兼容约束已经直接写入 RPC 计划 §4，没有另外的契约文档。

## 0. 本次重写依据的用户决定（2026-10-24）

1. **实验室版的核心是"共享资源 + 共享模型 + 用量管控"**，不是替成员执行任务的服务。成员始终用自己的账号、在自己的本机或自己的服务器账号里执行。
2. **有服务器时**：管理员在服务器上部署实验室服务器版，把成员加进群组；成员用自己的服务器账号登录，只能操作自己的数据；管理员定义共享资源包（插件、Skills、Wrapper 等，形式类似官网目录），共享已订阅的大模型 API，并查看、控制成员的资源使用。
3. **资源管控包含两层**：Phi 内的用量（模型调用、token、资源使用），以及服务器的系统资源（CPU、GPU、内存、磁盘、调度器作业）。
4. **模型 API 经实验室网关共享**：管理员的 key 只放在服务器上，不分发给成员。
5. **没有服务器时**：只做资源包共享和统一模型路由，不做成员管理和任务路由，本质上是个人版加团队功能。实验室资源不能放到 GitHub 这类公开平台，也不能依赖管理员一直在线。
6. **群聊、任务卡、Agent 委托、好友交流移到更后的版本**（§10）。
7. **服务器版的环境要共享复用**：Wrapper、内置环境、实验室自己的插件和技能所需的环境，在服务器上只维护一份，所有成员复用，而不是每人一份（§4.5）。原来"先实验室协作、再个人好友交流"的顺序在那个后续版本里继续有效。

默认假设（用户没有反对，开工前可以再改）：系统资源的"控制"第一版做到**统计和超额提醒**；强制限额只在管理员拥有 root 的服务器上做，学校公共集群上只做统计（§6）。

## 1. 三种形态

三种形态共用同一个客户端和同一个执行内核，不维护多套 Agent 执行实现。

| 方面     | 个人版                   | 团队包（无服务器）                                     | 实验室服务器版                                              |
| -------- | ------------------------ | ------------------------------------------------------ | ----------------------------------------------------------- |
| 适用     | 一个人独立使用           | 小团队没有自己的服务器，或暂时不想运维服务             | 实验室有一台管理员拥有 root 的 Linux 服务器                 |
| 成员身份 | 不需要                   | 每个成员一对 Phi 生成的密钥，管理员登记成员公钥        | 成员自己的服务器 Linux 账号                                 |
| 共享资源 | 无                       | 签名并按成员公钥加密的资源包，放在任意私有或公开存储上 | 服务器托管的私有签名目录，按群组授权                        |
| 共享环境 | 各自安装                 | 共享环境定义与锁文件，每个成员在自己机器上按定义安装   | 服务器上一份共享环境，管理员维护、成员只读复用              |
| 共享模型 | 各自配置                 | 模型服务商的组织子 key，加密后只发给对应成员           | 实验室网关转发，key 留在服务器                              |
| 用量管控 | 无                       | 由模型服务商后台统计和限额                             | 网关统计 Phi 用量；服务器统计系统资源，有 root 时可强制限额 |
| 执行位置 | 本机或个人 SSH/HPC       | 同个人版                                               | 成员在服务器上的自己账号（经现有 SSH 远程），或本机         |
| 常驻服务 | 无                       | 无，管理员发布完即可离线                               | 实验室服务器版一个服务进程                                  |
| 离线     | 本地文件、历史、已装资源 | 已安装的资源包继续可用；模型仍要联网                   | 服务器不可达时，个人项目照常；实验室资源与网关显示离线      |

通用规则：

- 加入团队或实验室不会自动上传个人文件、聊天、记忆或密钥。
- 一位用户可以同时加入多个团队和实验室；退出其中一个不影响个人空间和其他团队。
- 个人离线可用，指本地文件、历史和已安装能力不依赖 Phi 服务；云模型仍需联网。

## 2. 核心用户流程

### 2.1 实验室服务器版：部署与加入

1. 管理员在实验室服务器上安装实验室服务器版，完成初始化：设定实验室名称、管理员账号（必须是服务器上的真实 Linux 用户），配置模型 API 与资源目录。
2. 管理员创建群组，把成员的**服务器 Linux 账号**加入群组。可以映射到服务器已有的用户组，也可以在 Phi 里单独维护成员表。
3. 成员在自己的 Phi 客户端里添加实验室：填服务器地址，用自己的服务器账号登录（复用成员已经配置好的 SSH 密钥，或系统认证）。客户端显示服务器身份、实验室名称、管理员和数据说明，成员确认后加入。
4. 加入后，客户端多出这个实验室的资源目录和模型选项；成员在服务器上的项目继续通过现有 SSH 远程使用，执行身份就是成员自己的账号。

邀请只是一个方便加入的链接，本身不代替身份认证；身份认证始终是"能以该 Linux 账号登录这台服务器"。

### 2.2 团队包：创建与加入

1. 管理员在自己的 Phi 里创建团队，生成团队签名密钥（私钥只留在管理员本机，可导出备份）。
2. 成员在自己的 Phi 里生成成员密钥对，把**公钥**发给管理员（复制文本或扫码即可，不含任何秘密）。
3. 管理员把成员公钥登记进团队，选择要共享的资源和模型配置，点"发布"：Phi 生成一个新版本的团队包，用团队密钥签名，并按每个成员的公钥加密。
4. 管理员把发布结果上传到团队约定的存储位置（§4.3），然后就可以离线。
5. 成员在 Phi 里添加"团队来源"：填存储地址和团队公钥指纹。之后 Phi 定期拉取、验证签名、用成员私钥解密、安装更新。

### 2.3 使用共享资源

- 实验室或团队发布的资源，在成员的资源目录里显示为一个独立来源，带"来自 X 实验室/团队"的标记和版本号。
- 成员安装后的使用方式和个人资源完全一样；在服务器版里，资源可以预装在服务器的共享只读目录中，成员不用各自维护一套服务器安装。
- 资源升级不改变正在运行的任务；新任务使用新版本。管理员撤回某个版本后，客户端不再提供它给新任务。

### 2.4 使用共享模型

- 实验室服务器版：成员在模型选择里看到"X 实验室"提供的模型。请求发到实验室网关，由网关加上管理员的 key 转发给服务商。成员看不到 key。
- 团队包：成员拿到的是服务商为他单独签发的子 key，按他自己的额度使用。

### 2.5 查看用量与管控

- 管理员在管理台看到每个成员的：模型调用次数和 token、各共享资源的使用次数、服务器上的 CPU/GPU/内存/磁盘占用和调度器作业。
- 成员可以看到自己的用量和额度。
- 超出管理员设置的阈值时，提醒管理员和成员本人；在有 root 的服务器上，管理员可以启用强制限额（§6）。

## 3. 身份与权限

### 3.1 身份

| 形态           | 成员身份              | 认证方式                                                     |
| -------------- | --------------------- | ------------------------------------------------------------ |
| 实验室服务器版 | 服务器上的 Linux 账号 | 成员能以该账号登录服务器（SSH 密钥或系统认证），不另建密码库 |
| 团队包         | Phi 生成的成员密钥对  | 资源包按成员公钥加密；能解密就说明是该成员                   |

成员身份始终由可信入口确定（服务器的系统认证，或解密是否成功），不接受客户端自报的角色或用户名。

### 3.2 角色

只设两个角色，加一项可授予的发布许可：

| 操作                     | 管理员                  | 成员（有发布许可）     | 成员             |
| ------------------------ | ----------------------- | ---------------------- | ---------------- |
| 添加/移除成员、管理群组  | 允许                    | 不允许                 | 不允许           |
| 发布/撤回共享资源        | 允许                    | 允许（限被授权的资源） | 不允许           |
| 配置共享模型与额度       | 允许                    | 不允许                 | 不允许           |
| 查看用量                 | 所有成员                | 自己                   | 自己             |
| 访问成员自己的项目与数据 | 无此产品权限（见 §3.3） | 只能访问自己的         | 只能访问自己的   |
| 使用共享资源与共享模型   | 允许                    | 允许                   | 允许（在额度内） |

管理员转移、管理员账号恢复单独设计（§12）。不做自定义角色、逐字段权限或审批链。

### 3.3 数据边界

- "成员只能操作自己的数据"在服务器版里由操作系统保证：成员用自己的 Linux 账号执行，文件权限、进程归属都是系统层面的。Phi 不在这之上再造一套隔离。
- 管理员看到的是**用量和资源统计**，不是成员的对话、文件或记忆。Phi 不提供管理员读取成员会话的功能。
- 但服务器的 root 在技术上能读取服务器上的任何数据，Phi 不能也不承诺阻止这一点。加入实验室时要把这一点和实验室的数据政策一起展示给成员。
- 移除成员后：网关立即拒绝他的模型请求；资源目录不再向他提供新版本；他在服务器上的 Linux 账号是否保留由管理员在系统层面决定，Phi 不删除成员的文件。

## 4. 共享资源包

### 4.1 复用现有资源机制

Phi 已经有一套多来源、带签名的资源目录：内置来源、官方来源（`phi-packages`）、GitHub 来源和本地目录来源，并支持签名验证与可信公钥（[registries](../../src/main/agent/packages/registries.ts)、[signature](../../src/main/agent/packages/signature.ts)、[official-registry](../../src/main/agent/packages/official-registry.ts)）。团队包和实验室目录都作为新的来源类型接入这套机制，不另做一套安装和版本管理。

可共享的内容：插件、Skills、Wrapper、Agent 定义、MCP 连接器配置、环境定义，以及它们之间的依赖与版本固定。

### 4.2 版本与撤回

- 每次发布生成不可变的新版本；客户端记录正在使用的版本。
- 撤回只阻止新的使用，不影响在途任务。
- **已下载的内容收不回来**：被移除的成员拿不到之后的版本，但他已经拿到的版本无法远程删除。产品界面要如实说明这一点。

### 4.3 团队包：不公开、不依赖管理员在线

团队包的内容在发布时就**按每个成员的公钥加密**，并用团队密钥签名。因此：

- **放在哪里都安全**：学校网盘或 NAS、对象存储（阿里云 OSS、腾讯 COS、S3 等）、私有 Git 仓库，甚至公开位置，都只能被持有成员私钥的人解开；签名保证内容没被篡改。团队可以选自己机构允许的存储。
- **不依赖管理员在线**：发布之后，存储本身就是静态文件，管理员关机也不影响成员拉取。
- **加入和移除**：新成员要等管理员下次发布后才能解密；移除成员后，下次发布不再为他加密。
- **密钥丢失**：成员私钥丢失后，重新生成密钥对，请管理员重新登记并发布；团队私钥丢失需要重新建团队，所以创建时提示管理员备份。

### 4.4 实验室服务器版的资源目录

服务器托管一个私有的签名目录，只对已认证的群组成员开放下载；资源可以同时预装到服务器的共享只读目录，供成员在服务器上直接使用。服务器版也可以导出一份团队包，给不在服务器上工作的成员使用。

### 4.5 共享环境（服务器版）

Wrapper、内置环境（例如 phi-base）、实验室自己的插件和技能所需的环境，在服务器上**只维护一份**，所有成员复用。这样既省磁盘和安装时间，也保证大家用的是同一套软件版本。

**做法**：在现有受管环境机制上增加一个"共享环境根"。现在每个用户在自己的运行时根目录下有一个 micromamba 根（`pkgs/` 包缓存和 `envs/` 环境，见 [envs/runtime](../../src/main/agent/envs/runtime.ts)），并有租约和垃圾回收。服务器版增加一个由管理员维护的共享根，例如 `/opt/phi-lab/envs`：

| 内容                     | 位置                     | 谁能写             | 成员怎么用                                   |
| ------------------------ | ------------------------ | ------------------ | -------------------------------------------- |
| Wrapper 本体与其运行环境 | 共享根                   | 管理员（或发布者） | 只读使用，不需要各自安装                     |
| 内置环境（如 phi-base）  | 共享根                   | 管理员             | 只读使用                                     |
| 实验室插件、技能所需环境 | 共享根，随资源包版本发布 | 管理员（或发布者） | 只读使用；资源包声明它依赖哪个共享环境版本   |
| 成员自己额外需要的环境   | 成员自己的运行时根       | 成员本人           | 和现在一样；可以复用共享根的包缓存，减少下载 |

规则：

- **共享环境只读**：目录归管理员所有，对实验室群组只开放读和执行权限。成员不能在共享环境里装包；需要额外的包时，在自己的运行时根里建个人环境，或请管理员发布新版本。
- **按版本不可变**：共享环境每次变更都生成一个新版本，旧版本保留到没有任务在用为止。资源包和 Wrapper 固定依赖某个环境版本，所以升级不会影响正在运行的任务。
- **谁在用、何时回收**：成员的内核不能写共享根，所以"哪个版本还在被使用"由实验室服务器版统一登记（成员内核使用共享环境时向它报告租约），回收只由管理员执行，并且先核对没有在用的租约。
- **找环境的顺序**：成员内核解析一个环境时，先在共享根里找相同定义、相同版本的环境，找到就直接用；找不到再按现在的方式在成员自己的根里安装。
- **离线计算节点**：共享根放在计算节点也能访问的共享文件系统上（集群常见的 NFS/Lustre）。安装和更新只在能联网的节点上由管理员完成，计算节点只读使用，这正好适合计算节点不能联网的集群。
- **团队包（无服务器）不共享安装产物**，只共享环境定义和锁文件。每个成员按同一份锁文件在自己的机器上安装，得到相同的版本。

## 5. 共享模型

### 5.1 实验室网关（服务器版）

- 管理员把模型服务商的 API key 配置在实验室服务器上，key 不下发给任何客户端。
- 成员客户端把实验室网关当作一个模型来源；每个请求带成员身份，网关核对身份和额度后转发。
- 网关按成员记录调用次数、token 和费用估算，支持按成员、按模型设额度；撤权立即生效。
- 内核侧接入方式：网关是统一 RPC 计划里"模型访问"接口的第三种实现（本地直连、客户端代理之外），内核会话逻辑不用改（见 RPC 计划 CR3）。

### 5.2 团队包的模型路由

- 优先使用模型服务商自带的组织功能：例如 Anthropic Console 的 workspace、OpenAI 的 project、阿里云百炼的子账号，给每个成员单独签发 key 并设置额度。统计和限额由服务商负责，不需要自己运行网关。
- 每个成员的 key 只加密给这个成员，放在团队包里；撤权就是在服务商后台吊销他的 key。
- 只有需要跨多个服务商统一路由、而服务商的组织功能又不够时，才需要一个常驻网关。那时可以把网关部署在云函数或便宜的云主机上，同样不依赖管理员本机。

### 5.3 服务条款

共享的必须是 **API key**（组织账号或付费 API 账号）。把个人订阅账号（例如 ChatGPT、Claude 的会员订阅）共享给多人通常违反服务条款。产品不提供"共享订阅登录"功能，配置界面要写明这一点。

## 6. 用量与资源管控

### 6.1 Phi 内的用量

| 来源         | 统计内容                                | 能否强制限额                     |
| ------------ | --------------------------------------- | -------------------------------- |
| 实验室网关   | 每个成员的模型调用、token、费用估算     | 能，网关直接拒绝超额请求         |
| 资源目录     | 每个成员下载、安装、使用共享资源的次数  | 能，目录不再提供                 |
| 成员内核上报 | 成员在服务器上由 Phi 发起的任务数和时长 | 只统计；成员内核上报，不作为权威 |

### 6.2 服务器的系统资源

统计：普通账号通常就能读到大部分数据；如果服务器隐藏了其他用户的进程（例如 `/proc` 设置了 hidepid），则需要 root。按 Linux 用户汇总 CPU、内存、GPU（`nvidia-smi`）、磁盘（配额或目录占用），以及 Slurm 等调度器的作业记录（`sacct`）。

控制分两种情况：

| 服务器情况                      | 能做什么                                                                                       |
| ------------------------------- | ---------------------------------------------------------------------------------------------- |
| 管理员拥有 root                 | 统计 + 提醒；可选启用强制限额：systemd/cgroups 的单用户 CPU 与内存上限、磁盘配额、GPU 分配策略 |
| 学校公共集群（管理员没有 root） | 只统计 + 提醒；限额依赖集群已有的调度器配额（Slurm QoS 等），Phi 不尝试绕开                    |

第一版默认只做统计和超额提醒；强制限额作为 L2 阶段的可选功能（§8），启用前要在管理台明确展示将要修改的系统设置，由管理员确认。

## 7. 部署与运行责任

- **实验室服务器版**：一个服务进程，负责成员与群组、资源目录、模型网关、用量统计、管理台和备份。部署在管理员拥有 root 的那台服务器上。
- **执行**：成员在服务器上的任务由成员自己的 Phi 内核以成员自己的 Linux 账号运行，沿用当前版本的模型："每个主机 + OS 用户一个内核、经 `phi-helper attach` 连接"（见 [RPC 计划 §4](phi-kernel-implementation.md#collaboration-compatibility)）。实验室服务不替成员执行任务，也不持有成员的任务。
- **学校公共集群**：很多集群禁止在登录节点上常驻服务，计算节点也经常不能联网（例如 node3 所在集群）。这种环境下不部署实验室服务器版，用团队包共享资源和模型；如果需要统计集群用量，服务部署在另一台允许常驻的机器上，通过 `sacct` 等只读接口汇总。
- **团队包**：没有服务进程；发布由管理员在自己的 Phi 里完成，存储由团队自选。
- 认证、存储与网关的具体选型，在 L0 用成熟方案验证后确定。

## 8. 分阶段交付

以下全部属于**下一大版本**。当前 RPC 计划不等待这些功能，也不承担其工作量。时间为单主力 + Codex 的低置信度规划量级（规划判断，没有实测依据），开工前重估；不含当前 RPC 阶段和外部资源等待。

建议先做团队包：它不需要服务器、范围最小，而且资源包格式、加密和模型配置分发会被服务器版直接复用。

| 阶段            | 交付范围                                                                                                       | 放行条件                                                                       | 初步量级 |
| --------------- | -------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------ | -------- |
| L0 可行性验证   | 加密团队包原型（签名、按成员加密、私有存储拉取）；以服务器 Linux 账号认证；网关转发与按成员计量                | 三个测试成员各自解密并安装；被移除成员拿不到新版本；网关能按成员拒绝超额请求   | 2–3 周   |
| T1 团队包       | 团队与成员密钥管理、发布与撤回、团队来源、模型子 key 分发、客户端界面                                          | 两名成员在无服务器条件下复用同一资源版本和各自的模型 key；管理员离线不影响拉取 | 4–6 周   |
| L1 服务器版 MVP | 实验室服务器版安装与升级、成员与群组、私有资源目录、共享环境根（§4.5）、实验室网关、Phi 用量统计、管理台、备份 | 至少两名成员用自己的服务器账号登录并复用资源；越权、撤权、备份恢复验证通过     | 7–10 周  |
| L2 系统资源管控 | 按用户统计 CPU/GPU/内存/磁盘与调度器作业；超额提醒；有 root 时的可选强制限额                                   | 统计与系统实际一致；强制限额启用前后可核对；公共集群模式只读不越权             | 3–5 周   |

下一大版本合计约 16–24 工程周（L1 含共享环境根，比不含时多约 1–2 周）。群聊、任务卡、委托、好友等协作功能不在此列（§10）。

## 9. 验收与试点

试点建议：一个团队包试点（3–5 名成员、无服务器）和一个服务器版试点（一台管理员有 root 的 Linux 服务器、最多十名成员），各连续试用十个工作日。

| 阶段 | 验收场景                   | 成功标准                                                                                                              |
| ---- | -------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| T1   | 管理员发布后离线           | 成员照常拉取、验证、解密、安装                                                                                        |
| T1   | 资源包放在公开位置         | 非成员拿到文件也无法解密；篡改后的包被拒绝                                                                            |
| T1   | 移除成员后再发布           | 被移除成员拿不到新版本；界面如实说明旧版本无法收回                                                                    |
| T1   | 模型子 key 吊销            | 被吊销成员的请求失败，提示清楚；其他成员不受影响                                                                      |
| L1   | 成员用自己的服务器账号登录 | 只能看到和操作自己的项目与数据；不能借用其他成员身份                                                                  |
| L1   | 共享模型                   | 成员客户端拿不到 key；按成员计量准确；超额被拒绝；撤权立即生效                                                        |
| L1   | 共享环境                   | 两名成员使用同一份 Wrapper 与内置环境，没有各自安装；成员无法改动共享环境；升级环境不影响在途任务；有租约时回收被拒绝 |
| L1   | 资源升级与撤回             | 在途任务版本不变；新任务用新版本；撤回后不再提供                                                                      |
| L1   | 服务器不可达               | 个人项目和历史照常可用；实验室资源与模型明确显示离线                                                                  |
| L1   | 备份与恢复                 | 成员、群组、目录、额度一致恢复；旧令牌不错误复活                                                                      |
| L2   | 系统资源统计               | 与 `ps`、`nvidia-smi`、`sacct`、磁盘配额的实际值一致                                                                  |
| L2   | 强制限额（有 root）        | 启用前展示将修改的系统设置；启用后超额进程被限制；关闭后恢复原设置                                                    |

价值指标：至少两名成员复用同一共享资源版本、至少五次真实科研任务使用了共享资源或共享模型；管理员能说清每个成员用了什么、用了多少。

## 10. 移到后续版本的协作功能

以下功能整体移出本大版本，等资源共享与用量管控稳定后再规划，届时仍按"先实验室协作、再个人好友交流"的顺序：

- 项目群聊、文本与附件消息。
- 任务卡、任务分派、转交、交付与验收。
- 人与 Agent、Agent 与 Agent 的委托和自动协作（委托深度、预算、防循环等）。
- 好友、私信、小群、跨团队分享，以及开放给他人调用的在线 Agent 服务。
- 服务端持有任务、持久队列、审批收件箱（原计划中支撑协作的部分）。

这些功能需要的接口位置已经在当前 RPC 计划的 CR2、CR4、CR6 中保留（§11），不会因为后移而让现在的内核把单机假设写死。

## 11. 对当前 RPC 计划的兼容要求

只提出以下设计约束，已经写入[当前计划 §4](phi-kernel-implementation.md#collaboration-compatibility)：

| 兼容约束       | 当前版本做什么                                                                                                                 | 下一大版本才做什么                                                                  |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------- |
| CR1 调用上下文 | 可信入口构造调用上下文；执行身份就是运行内核的 OS 账号，不与 Phi 会话或 SSH 主机名混为一谈                                     | 成员身份（服务器 Linux 账号或团队成员密钥）与群组归属                               |
| CR2 协议与标识 | 保留现有标识，提供版本/能力协商和关联扩展方式                                                                                  | 用量上报字段；更后版本的多人会话与任务交接                                          |
| CR3 权限与凭据 | 保留准入、审批、凭据解析接口；模型访问做成可替换接口                                                                           | 第三种模型访问实现：实验室网关（按成员身份与额度）                                  |
| CR4 生命周期   | 区分断线、取消和退出；内核寿命与连接分开（socket + 宽限期）                                                                    | 本大版本不需要服务端持有任务；更后的协作版本再考虑                                  |
| CR5 资源与数据 | 资源解析/版本/执行分离；资源来源可扩展（多来源、各自的签名公钥）；可信配置提供存储根；环境解析允许多个环境根，其中可以有只读根 | 团队包来源（签名 + 按成员加密）、实验室私有目录来源、共享只读环境根与跨用户租约登记 |
| CR6 事件与宿主 | 执行事件脱离 UI，按会话路由，能力显式注册；资源与模型使用事件可被统计                                                          | 用量统计上报；更后版本的多人订阅与通信                                              |

当前版本不因此新增个人身份文件、实验室适配替身或完整未来字段。兼容目标是避免把单机假设固定在内核中，不承诺未来零重构。

## 12. 待细化决策与项目控制

L0 前明确：

- 团队包使用的加密方案与密钥格式（优先采用成熟的公开方案，不自创加密）。
- 服务器版认证方式：复用 SSH 密钥、系统认证（PAM）还是两者都支持。
- 网关选型：自研轻量转发，还是集成成熟的开源网关。
- 管理员转移与恢复、成员离开后的数据归属说明、备份与运维负责人。
- 系统资源强制限额具体用哪些系统机制，以及关闭时如何恢复原设置。
- 共享环境根的位置与文件系统（计算节点能否访问）、群组权限设置方式、跨用户租约的登记与回收流程。

每周演示一个完整场景，每两周更新剩余估算。阶段超过上限 20% 时调整范围或人力，不削减身份、撤权、加密、额度和数据保护验收。

个人数据默认私有；团队和实验室共享的只是资源和模型能力；复制资源文件不构成成员授权。完整数据政策和收费方案另行确定，不能隐藏在当前内核改造中。

本文件是下一大版本的规划，不是开工指令。当前执行范围始终由另一份 RPC 计划确定。
