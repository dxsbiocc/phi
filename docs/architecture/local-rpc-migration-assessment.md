# 本地会话改走 OMP RPC：迁移评估

日期：2026-10-24
基线：本地 main `c6387963`（含 plan-execute E3）
状态：**已被取代（2026-10-24）**。本文"本地改走 OMP CLI RPC"的方向已被否决，以 [PHI 本地与远程统一 RPC 计划](../roadmap/phi-kernel-implementation.md)为准（否决依据见其 §13）。本文只保留作为测量数据（第 3 节，摘要见计划 §8.1）和能力缺口清单（第 2 节，已并入计划 §18.3 的 K0 账本）的来源；第 0 节结论和第 4 节分步计划不再有效。

## 0. 结论

- 可行，值得做。做完后本地和远程只差"怎么启动 OMP 进程"（本机起子进程 vs SSH），会话层只剩一份代码。
- 先纠正一个说法：本地现在其实**不是进程内**。它也是一个独立的 Bun worker 进程（`engine/in-process/main.ts`），只是里面嵌着 OMP SDK，跟桌面端走的是 Phi 自己的私有协议。所以两边早就都在进程外了，真正的差别是**两套协议**：本地是 Phi 私有协议加 SDK 直调，远程是 OMP 官方 RPC 加 Phi 扩展。
- 重复是持续发生的。刚合入的 plan-execute E3 就只做了本地：`plan-steps` 扩展、`session.plan.enter`、主进程主动启动子任务（`agentRuns.start`）在远程都还没有。
- 主要代价是**每个会话一个 OMP 进程**。本地应当用 OMP 官方的单文件版（和远程同一种发布物），而不是 bun 跑 `cli.js`。S0 实测（第 3 节）：单文件版加完整 Phi 扩展，约 0.3 秒就绪、约 280–310 MB/进程。现在共用 worker 的方式是新建会话约 65 毫秒，每多一个会话只多 15–25 MB。
- S0 新发现一个大缺口：远程的 Phi 扩展把原生 `read` 限制为只读文本文件（G8）。本地切过去之前必须先放开，否则本地会失去读 PDF、图片、Office 文件的能力。
- T11 现在不影响本地：本地会话由 worker 直接调模型提供商，不经过模型网关。切换后会不会受影响，取决于本地 OMP 怎么拿模型凭据（第 5 节 D3）。
- 建议顺序：先在 RPC 上补齐缺口（远程同时受益，和现有路径不冲突），再切本地，最后删掉旧路径。

## 1. 现状：两条会话链路

|                    | 本地                                                                                                  | 远程                                                                                                            |
| ------------------ | ----------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| 进程               | 桌面端拉起一个 Bun worker，所有本地会话共用                                                           | 每个会话一个 `omp --mode rpc`，跑在服务器上                                                                     |
| 协议               | Phi 私有 JSON 行协议（`session.create`、`session.prompt`、`agentRun.start`……约 50 个方法）            | OMP 官方 RPC v2，外加宿主工具、`extension_ui_request` 等                                                        |
| OMP 怎么接         | worker 里直接 `createAgentSession`，用 SDK 对象                                                       | `-e` 加载 Phi 扩展包 `phi-extension/rpc-entry.ts`                                                               |
| 扩展集合           | `createMainSessionExtensions`：下一步建议、计划审阅守卫、计划步骤、项目边界、URL 守卫、专家回退、审批 | `rpc-entry.ts`：项目边界、URL 守卫、Cursor 恢复、模型选择、压缩、提示、执行授权、原生流、子任务、审批、宿主结果 |
| 会话驱动（桌面端） | `in-process-engine.ts` 直接转发请求                                                                   | `rpc/facade-session-driver.ts`、`remote-session-runtime.ts` 等（`engine/rpc/` 共 16.8k 行）                     |
| 路由               | `SessionRoutingEngine`：属于远程的会话交给 RPC 驱动，其余走 `legacy`（即本地 worker）                 | 同左                                                                                                            |

worker 里除了会话，还托管着一些**和项目位置无关的桌面服务**：决策模型、模型登录与快照、MCP 授权、联网搜索设置、项目记忆读写、模型网关租约。远程会话也在用这些服务（比如 `readRpcCompactionPolicy` 就是向 worker 请求的）。迁移时它们原样保留，只迁"会话"这一块。

### 2.2 扩展只加载在本地

| 扩展                        | 作用                   | 远程                                       |
| --------------------------- | ---------------------- | ------------------------------------------ |
| `next-action`               | 每轮结束给出下一步建议 | 没有加载                                   |
| `plan-review`、`plan-steps` | 计划模式（同 G1）      | 没有加载                                   |
| `specialist-fallback`       | Phi 专家智能体的回退   | 远程改用可信 agent 定义和 `task`，机制不同 |
| `environment-binding`       | 专家会话绑定环境       | 远程用 `rpc-child-environment`，机制不同   |

前两项是纯缺失，直接并入 `rpc-entry`。后两项远程有自己的等价实现：迁移时保留 RPC 版，删掉本地版。

### 2.3 已经有两份实现的能力（不缺，但重复）

这部分不是 RPC 缺能力，而是同一件事写了两遍，迁移后可以删掉本地那份：

### 2.4 不受影响的部分

- **辅助会话**：标题生成（`index.ts`）、人设生成、Notebook 代码生成、终端草稿，都在主进程里直接 `createAgentSession`，而且大多是 `noTools`，跟执行位置无关。这次不迁，以后想统一可以单独开一个"辅助模型调用"接口。
- **worker 里的桌面服务**（第 1 节最后一段）：保留。
- **上游缺口 T11**（S0 已查清）：问题出在模型网关（`in-process/model-gateway*.ts`，由 `rpc/model-proxy-lease.ts` 申请租约）上。OMP 的 side/advisor/maintenance/autolearn 等辅助调用经过网关时会丢 opaque thinking，主通道已修复。这个网关**只给远程会话用**；本地会话的 SDK 直接用 worker 里的凭据调提供商，从来不经过网关，所以**本地现在不受 T11 影响**。切换后：如果本地 OMP 也经 Phi 模型代理调模型，T11 就会跟着到本地；如果本地 OMP 直接读 Phi 的凭据目录，就不受影响。这是一个设计决定（第 5 节 D3），不是硬门槛。

### 2.5 RPC 路径里本地用不上的东西

本地传输要跳过：SSH、phi-helper、服务器运行时根目录、OMP 二进制上传、反向隧道。还要核对 `execution-authority`、`session-verification`、`bootstrap-attestation` 这几项有没有隐含"一定是远程"的假设。模型代理可以照用，只是监听在本机 `127.0.0.1`，不经过隧道。

## 3. 本地启动开销实测（S0，2026-10-24）

### 3.1 测法

- 机器：本机 macOS，Apple Silicon（arm64）。所有数字都受机器负载影响，同一项在不同轮次之间会有约 ±20% 的波动。
- **单文件版**：OMP 官方 v18.10.3 发布页的 `omp-darwin-arm64`（217 MB），SHA256 与官方 `SHA256SUMS.txt` 一致；同一份清单里的 `omp-linux-x64` 也和 `rpc/runtime-deployment/manifest.ts` 里的一致。
- **bun 版**：`bun node_modules/@oh-my-pi/pi-coding-agent/dist/cli.js`。
- **完整 Phi 扩展**：用测试夹具 `tests/engine-contract/bootstrap-stdio-fixture.ts` 的同一套参数（`-e rpc-entry.ts`、bootstrap 配置、启动证明 `attestBootstrap`），只多加了一个开关，用来改成单文件版启动。
- **对话**：本机脚本化模型（`tests/engine-contract/loopback-model.ts`，真实 SDK 解析流式响应），每轮先调一次 `read` 读项目文件，再回一段文字。**没有接真实提供商**，原因见 3.4。
- **对照（现在的方式）**：一个 Bun 进程加载 SDK，依次 `createAgentSession` 4 个会话，每个跑 5 轮同样的对话。
- **扩展的运行方式**：用的是 bootstrap 模式（没有运行时配置），不加载提示、压缩、子任务、执行授权这些运行时扩展，但扩展代码已经全部加载。运行时模式多出来的只是读几份配置和挂事件处理，预计对时间和内存影响很小（**推测**）。
- 脚本：`.phi-acceptance/s0-measure/`（git 已忽略）下的 `measure-rpc-entry.ts`、`fixture.ts`、`measure-shared-sdk.ts`；不带扩展的测法见 `/private/tmp/claude-501/-Users-dengxsh-Downloads-Work-App-Phi/c2fdb84f-9f92-411a-808c-15b3770d2df9/scratchpad/measure-local-rpc-exec.mjs`。

### 3.2 结果

每会话一个进程（时间从拉起进程算起，到 `ready` 帧或完成启动证明为止）：

| 方式                                                   | 就绪耗时        | 空闲内存       | 20 轮后        | 50 轮后 |
| ------------------------------------------------------ | --------------- | -------------- | -------------- | ------- |
| 单文件版，不带扩展，HOME 已预热                        | 0.32–0.42 s     | 269–280 MB     | —              | —       |
| **单文件版 + 完整 Phi 扩展，HOME 已预热**              | **0.27–0.31 s** | **277–288 MB** | **305–313 MB** | —       |
| 单文件版首次运行（HOME 是空的，要解出约 94 MB 原生库） | 1.36–1.65 s     | 441–476 MB     | —              | —       |
| bun 版，不带扩展                                       | 0.70–1.0 s      | 464–491 MB     | —              | —       |
| bun 版 + 完整 Phi 扩展                                 | 0.87–1.13 s     | 552–571 MB     | 581–597 MB     | 622 MB  |

共用一个进程（现在 worker 的方式）：

| 会话数          | 进程内存   | 新建该会话耗时 |
| --------------- | ---------- | -------------- |
| 0（只加载 SDK） | 337–341 MB | —              |
| 1               | 434–444 MB | 178–190 ms     |
| 2               | 450–459 MB | 61–67 ms       |
| 3               | 476–486 MB | 66 ms          |
| 4               | 490–501 MB | 64–66 ms       |

协议协商（`negotiate_protocol` v2）和 `get_state` 加起来只要 5–30 ms，可以忽略。单轮对话时间在两种方式下都是约 10 ms（脚本模型，不代表真实模型的耗时）。

### 3.3 结论

- **本地必须用单文件版**，不要用 bun 跑 `cli.js`。单文件版启动快约 3 倍、内存少约一半，而且跟远程是同一种发布物，下载、校验、缓存的代码可以复用（`runtime-deployment/` 加一个 macOS/Windows 条目）。
- **HOME 要固定、共享**。单文件版第一次在某个 HOME 下运行时要解出约 94 MB 原生库（多花约 1.2 秒）。本地所有会话应该共用一个 Phi 专用的 OMP HOME，只付一次。这也顺带解决了远程"每个会话复制一份 natives（约 227 MB）"的已知问题。
- **对比现在的方式**（4 个会话）：
  - 共用 worker：约 500 MB；新建会话约 65 ms。
  - 单文件版每会话一个进程：约 4 × 300 MB ≈ 1.2 GB；新建会话约 0.3 秒。
  - 也就是说，每多一个活动会话，大约多 260–280 MB 内存、多 0.2–0.25 秒启动时间。
- 对话本身带来的内存增长很小，每轮约 1 MB，20 轮约 +25–30 MB。所以内存主要取决于**同时活着的进程数**，跟聊了多久关系不大。
- 缓解办法（S4 实施）：
  1. 空闲会话超时就释放进程，下次发消息时从会话文件恢复（远程已有 `session-recovery.ts`）。
  2. 预热一个备用进程，把约 0.3 秒的启动延迟藏掉；不预热，用户也基本察觉不到。
  3. 运行中会话本来就限 4 个，所以常驻上限大约 4 × 300 MB 再加上备用进程。

### 3.4 没测到的部分

- **真实提供商**：会用到用户的模型凭据和额度，而且 OMP 必须读到 Phi 的凭据目录，所以这次没做。从机制上说，真实提供商只会让单轮的流式数据更大，对常驻内存影响很小（**推测**）。如果需要实测，可以用一个测试 API key，在空白 HOME 里跑一次。
- **Windows**：没测。官方 `SHA256SUMS.txt` 里有 `omp-windows-x64.exe` 和 `omp-windows-arm64.exe`。
- **真实项目资源**：没测带 MCP、技能、大型项目时的启动时间；这些在两种方式下都要付，不会改变上面的对比结论。

## 4. 分步计划

原则：前几步只**补** RPC，不动本地路径，每一步都能单独合入、单独让远程受益；本地切换放在缺口补齐之后；不留长期双轨。

| 步骤                          | 内容                                                                                                                                                                                                                                                                                                                     | 完成标准                                                                                        | 依赖           |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------- | -------------- |
| **S0 测量补齐** ✅ 2026-10-24 | 单文件版启动和内存、完整加载 `rpc-entry`、多轮对话后的内存、T11 是否影响本地                                                                                                                                                                                                                                             | 完成，见第 3 节、2.4 节 T11 条和 G8；真实提供商与 Windows 未测（3.4）                           | —              |
| **S1 本地传输**               | 新增本机 stdio 工厂（和 `ssh-stdio-factory.ts` 并列）以及本地版启动事务：本机直接拉起**单文件版** OMP，所有会话共用一个 Phi 专用 OMP HOME，跳过 helper/上传/隧道；模型凭据按 D3 的决定接。`runtime-deployment/manifest.ts` 加 macOS/Windows 条目（下载、校验复用）。开发期间用一个**临时**环境变量控制，只给开发和测试用 | 本地项目能用 RPC 完成一轮对话、审批、中断、恢复；现有测试全过                                   | S0、D3         |
| **S2 补齐缺口**               | 按顺序做：**G8 原生 read 放开（本地切换前必须完成）** → G3 prompt 选项 → G1 计划模式（含两个扩展）→ G2 主进程启动子任务 → `next-action` 扩展 → G4 shell 任务 → G5 分叉 → G6。每项都实现在 `rpc-entry` 或 RPC 驱动里                                                                                                      | 每一项远程都能用（G8 远程按服务器能力逐项放开）；`RemoteSessionCapabilityError` 的调用点只剩 G7 | 可以和 S1 并行 |
| **S3 扩展包统一**             | 本地也只从 `rpc-entry` 加载扩展，`createMainSessionExtensions` 只服务旧路径，直到 S5 删除                                                                                                                                                                                                                                | 两边加载的扩展集合由同一份配置决定                                                              | S1、S2         |
| **S4 默认切换**               | 本地新会话默认走 RPC；本地旧会话用 OMP 会话文件续上（两边都是 OMP 格式，大概率能直接打开，要实测）；加空闲释放和预热                                                                                                                                                                                                     | 全量测试通过；本地实机场景脚本（参照 `scripts/remote-r8.ts`）三场景通过；一轮人工界面检查       | S3             |
| **S5 删除旧路径**             | 删除 worker 里的会话部分（`session-creation`、`session-runtime`、`tool-registry`、`subagents`、`agent-run-start` 等）和 `SessionRoutingEngine` 的 legacy 分支；worker 只保留桌面服务；删掉 S1 的临时开关                                                                                                                 | `engine/in-process/` 只剩桌面服务；没有按本地/远程分流的会话代码                                | S4 稳定        |
| **S6 工作区宿主收口**（独立） | 功能代码不准直接判断本地还是远程。例如 `wrappers/remote-results.ts`、`content/remote-project-skill-service.ts` 直接 import `remote-workspace-read`，应该改为通过 `workspace-host`。在 `check:architecture` 里加一条规则，现有的位置先列入白名单，以后改到哪里收到哪里                                                    | 新增的 `isRemote` 类分支会被检查拦下                                                            | 无             |

说明：

- S6 跟引擎迁移无关，解决的是另一半重复（文件、上传、Notebook、Wrapper）。其中也有一部分是**远程本身就有的复杂度**，比如 Slurm 提交、结果回传、离线计算节点（`wrappers/` 下的远程专用代码约 4.6k 行，本地约 0.3k 行）。这部分收口之后也不会消失，只会被关进宿主接口后面。
- 工作量粗估（不含审核和实机）：S1 中、S2 中–大（G1、G2 是大头）、S3 小、S4 中、S5 中（主要是删代码和改测试夹具）。

## 5. 风险与待定决定

需要用户拍板的决定：

- **D1 内存**：单文件版每个活动会话约 280–310 MB；4 个会话约 1.2 GB，现在约 500 MB。需要决定空闲多久释放进程、最多保留几个常驻进程。
- **D2 启动延迟**：单文件版新会话约 0.3 秒，现在约 65 ms。要不要预热备用进程（多占约 280 MB）？
- **D3 本地模型凭据怎么接**，二选一：
  - (a) 本地 OMP 直接读 Phi 的凭据目录，和现在的 worker 一样：不经过网关，不受 T11 影响。但多个 OMP 进程会同时读写同一份凭据，OAuth 刷新可能互相冲突，需要先验证 OMP 对多进程的处理。
  - (b) 本地也经 Phi 模型代理，和远程一样：凭据只在桌面端，两边完全一致。但 T11 会跟着到本地，辅助通道丢 opaque thinking 的问题会出现在本地。
  - 建议先选 (a)，等上游修了 T11 再考虑统一到 (b)。

其他风险：

1. **G8 原生 read**：远程扩展的只读文本限制如果原样用到本地，会是明显退化（读 PDF、图片、Office 文件）。S2 要先做这一项。
2. **测试夹具**：大量测试直接驱动 worker 里的 SDK 会话。S5 要把它们迁到 RPC 夹具上，要求至少一条测试走真实的生产入口（吸取 d2629aa7 的教训）。
3. **OMP 升级**：只剩 RPC 一条路之后，OMP 的 RPC 协议和扩展 API 就是唯一的接缝。升级时要加协议覆盖测试，好处是现在要测两条路，以后只测一条。
4. **安装包体积**：macOS 单文件版约 217 MB。可以按需下载（复用远程的断点续传和校验），也可以打进安装包。要决定用哪种。
5. **内测范围**：路线图把可靠的本地桌面工作台定为内测成功标准，而 S4 动的正是本地主路径。建议 S0–S3 随时可做（不改本地行为），S4 选在一个稳定窗口切换。
